# 시켜줘, 명예소방관 — 공공데이터 기반 개인 맞춤형 이상상황 알림 플랫폼

> peterju.cloud 사이드 프로젝트 #3 — FDE(Forward Deployed Engineer) 지원용
> 작성일: 2026-07-13 · 상태: 초안 (v0.3, 함께 수정 중)

### 프로젝트명에 대한 메모
"시켜줘, 명예소방관" — 드라마 대사 인용이라 유머·기억성은 확실히 좋음. 다만 처음 보는 사람(특히 이름만으로 서비스를 유추해야 하는 채용 담당자)에게는 기능이 직관적으로 안 읽히는 게 트레이드오프. WEATHER처럼 "뭘 하는 앱인지 이름에서 바로 보이는" 네이밍 톤과는 결이 다름.
제안: **메인 타이틀은 "시켜줘, 명예소방관"으로 쓰고, 바로 아래 한 줄 설명("우리 가족에게 닥친 위험만 걸러서 알려주는 안전 알림 서비스")을 항상 같이 붙이는 방식**이면 유머와 명확성을 둘 다 가져갈 수 있을 듯. 이렇게 갈지, 좀 더 설명적인 이름으로 바꿀지는 12절에서 계속 논의.

## 1. 왜 이 프로젝트인가

### 1-1. 문제 정의
최근 몇 년간 이상기온, 이상기후, 재난 상황(지진, 태풍, 폭염, 폭우 등)이 예측하기 어렵게 발생하고 있고, 이에 대한 정보도 여러 기관·채널에서 파편적으로 쏟아진다. 정작 나 자신이나 내가 아끼는 사람(부모님, 자녀, 애인)에게 그 상황이 실제로 위험한지, 얼마나 급한지는 각 정보를 스스로 조합해야만 알 수 있다.

기상청 특보와 재난문자는 모두 신뢰할 수 있는 공공데이터지만, 이 데이터는 "지역" 단위로만 존재하고 "이 정보가 우리 부모님께 위험한가"라는 질문에는 답하지 않는다. 이 프로젝트는 그 갭 — 공식 데이터의 신뢰성과 개인의 실제 필요 사이의 갭 — 을 메우는 것을 목표로 한다.

이 문제 정의 방식 자체가 FDE 채용에서 요구하는 "현장에서 문제를 발견하고 진단한 경험" 서사와 맞닿아 있다 (채널톡 JD가 이력서에 명시적으로 요구하는 항목).

### 1-1a. 이 프로젝트가 풀려는 갭 — 실제 사례로 본 검증
2023년 7월 청주 오송 궁평2지하차도 침수 사고(미호강 범람, 14명 사망)의 정부 감찰 결과를 보면, 사고 지점(미호천교)의 홍수경보는 사고 4시간 17분 전에 이미 발령돼 있었다. 그런데 이건 기상청의 일반 호우특보(시군 단위)가 아니라 하천 수위 관측소 단위로 발령되는 홍수특보였고, 이 세분화된 위험 신호가 "이 지하차도가 위험하다"는 형태로 개인에게 전달되지는 못했다.

즉 데이터 자체는 이미 실시간으로 공개돼 있었지만, 그 데이터를 특정 위치·특정 사람에게 의미 있는 형태로 전달하는 last-mile이 비어 있었다는 뜻이다. 이 프로젝트가 정확히 그 자리를 겨냥한다 — 재해를 예측하는 게 아니라, 이미 존재하는 공식 위험 신호를 더 구체적인 위치와 사람에게 더 빨리 전달하는 것. (자세한 데이터 검증은 6절 참고)

### 1-2. 한 줄 정의
**"지역 + 인물"을 등록하면, 그 조합에 실제로 위험한 공공 이상상황만 걸러서 알려주는 개인화 알림 플랫폼.**

### 1-3. 핵심 차별점
기존 재난문자/기상특보 앱은 "지역 단위 전체 정보"를 그대로 뿌린다. 이 프로젝트는 지역에 "인물 프로필"을 결합해 위험도를 재계산한 뒤, 정말 중요한 알림만 남기는 필터링 레이어를 추가한다.

## 2. 핵심 유스케이스

### 2-1. 구독 모델: 지역 × 인물
사용자는 "지역 + 인물(관계, 나이대, 고려사항 태그)" 조합을 여러 개 등록할 수 있다.

예시:
- `대전 유성구 / 부모님 (고령, 보행보조필요)` → 폭염·한파 경보에 민감하게 반응
- `서울 강남구 / 본인 (성인, 운전자)` → 호우·태풍 경보 시 도로 위험 위주
- `부산 해운대구 / 자녀 (청소년, 실외근무/통학통근 중)` → 태풍·호우 시 등하교 관련 경보 우선

### 2-1a. 인프라 지점 매칭 (확장 유스케이스)
지역 단위보다 더 세밀하게, "이 지하차도/이 다리를 매일 지나간다"를 등록할 수 있게 하는 확장 기능. 하천 수위 관측소 데이터와 지하차도·교량 위치 데이터를 지리적으로 매칭해서, 근접한 관측소가 홍수특보 수준에 도달하면 그 지점을 지나는 사람에게 개별 알림을 준다 (6-1절 검증 결과 기반, Phase 5 확장 후보).

### 2-2. 개인화 알림 흐름
1. 공공데이터 소스에서 이상상황 이벤트 수집 (예: "대전 유성구 폭염경보 발령")
2. 시스템이 등록된 지역×인물 조합 중 해당 지역을 구독 중인 항목을 조회
3. 인물 프로필(연령대, 고려사항 태그)과 이벤트 유형을 위험도 판단 로직(4절)에 통과시켜 risk_level 산정
4. 임계치를 넘는 경우에만 LLM이 상황을 자연어로 요약해 웹/앱 푸시로 발송 ("유성구에 폭염경보가 발령됐어요. 보행보조가 필요하신 부모님은 낮 시간 외출을 피하시는 게 좋아요.")

### 2-3. MVP에서 다루는 재난 카테고리 (1차 범위)
- 기상특보: 폭염, 한파, 호우, 태풍, 대설
- 지진 / 지진해일
- 홍수특보 (홍수통제소 수위 관측소 단위, 6-1절) — 관측소를 관할 시군에 매핑해서 "OO 인근 하천에 홍수경보가 발령됐어요, 주변 저지대·지하차도 등에 침수 위험이 있을 수 있어요" 수준의 지역 단위 알림으로 MVP에 포함
- 긴급재난문자 (위 카테고리 외 전반 커버용 보조 소스)

**정밀 지점 매칭은 Phase 5로 분리**: "이 지하차도를 매일 지나간다"까지 등록해서 개인화하는 인프라 지점 매칭(2-1a)은 하천 관측소 ↔ 지하차도/교량을 지리적으로 매칭하는 추가 로직이 필요해서 확장 단계로 미룸. MVP는 정밀 매칭 없이 "관측소 관할 지역"만으로 홍수경보 알림을 준다 — 오송 사고 기준으로도 이 수준의 지역 알림만으로 "위험 신호가 이미 몇 시간 전에 발령됐다"는 정보는 확실히 전달할 수 있었다.

> **지반침하(싱크홀) 제외 결정**: 데이터포털 메타데이터를 확인한 결과 "표준데이터셋 갱신주기: 수시" vs "오픈API 업데이트 주기: 실시간"이 서로 상충되고, 실제 상세기능 대부분이 지하안전평가·지하개발사업 같은 행정 데이터이며 사고 즉시 반영되는 실시간 경보성 데이터인지 확인이 안 됨. "실시간 수집이 안 되면 뺀다"는 원칙에 따라 MVP에서 제외. 추후 실제 API 응답을 받아 실시간성이 확인되면 확장 소스로 재검토.

## 3. 인물 프로필 태그 체계

개인정보 민감도를 낮추기 위해 자유 텍스트 대신 **미리 정의된 태그**로만 입력받는다. 의학적 진단이 아니라 "본인이 체감하는 취약점"을 반영하는 수준으로 단순화.

**연령대 (단일 선택)**
`영유아/아동` · `청소년` · `성인` · `고령`

**고려사항 태그 (다중 선택)**
`운전자` · `보행보조필요` · `주의력낮음` · `판단력저하` · `운동능력낮음` · `임신부` · `호흡기·심혈관질환` · `실외근무/통학통근 중`

## 4. 위험도 판단 로직 — 규칙 + AI 하이브리드

### 설계 원칙
안전 알림에서는 "중요한 걸 놓치는 것"이 "덜 중요한 걸 보내는 것"보다 훨씬 나쁘다. 그래서 **결정론적 규칙 매트릭스를 기본 안전망으로 두고, AI는 그 위에서 판단을 보완·설명하는 역할**로 한정한다. (LLM 단독 판단은 hallucination·일관성 문제가 있어 안전 도메인에는 그대로 쓰지 않음 — 이 자체가 실제 엔터프라이즈 AI 제품에서 쓰는 guardrail 패턴이라 FDE 인터뷰에서 설명하기 좋은 지점)

### Layer 1 — 결정론적 위험도 매트릭스 (기본 안전망)
아래 조합은 항상 이 값을 그대로 따른다.

| 이벤트 | 트리거 조건 | Risk |
|---|---|---|
| 폭염특보 | 고령 | HIGH |
| 폭염특보 | 운동능력낮음 / 판단력저하 / 영유아·아동 | HIGH |
| 폭염특보 | 그 외 성인 | MEDIUM |
| 한파특보 | 고령 / 보행보조필요 | HIGH |
| 호우·태풍특보 | 운전자 | HIGH |
| 호우·태풍특보 | 실외근무/통학통근 중 | HIGH |
| 지진 (규모 4.0 이상) | 전원 | HIGH |
| 지진 (규모 3.0~4.0) | 보행보조필요 / 판단력저하 | HIGH |
| 지진 (규모 3.0~4.0) | 그 외 | MEDIUM |
| 대설특보 | 고령 / 보행보조필요 / 운전자 | HIGH |
| 홍수특보(경보) — 관측소 관할 지역 단위 (MVP) | 전원 | HIGH |
| 홍수특보(주의보) — 관측소 관할 지역 단위 (MVP) | 운전자 / 보행보조필요 | MEDIUM |

이 표는 시작점일 뿐이고, 실제 값(예: 지진 규모 임계치, 홍수특보 발령 기준)은 기상청·홍수통제소 발표 기준과 대조해 다음 단계에서 더 다듬을 예정. 홍수특보 행은 MVP에서는 관측소 관할 지역 단위로 바로 적용하고, Phase 5에서 지하차도/교량 단위 정밀 매칭(2-1a)으로 정교화한다.

### Layer 2 — AI 보조 판단 (매트릭스가 커버 못하는 케이스)
- 매트릭스에 명시적으로 없는 이벤트×태그 조합(예: 여러 태그가 동시에 걸린 복합 케이스, 긴급재난문자의 자유 텍스트 내용)은 LLM이 이벤트 컨텍스트 + 인물 태그를 입력받아 `risk_level`과 판단 근거를 함께 생성한다.
- Layer 1 매트릭스를 프롬프트에 few-shot 예시로 포함시켜, AI가 기존 규칙의 판단 기준선을 벗어나지 않고 그 논리를 확장하도록 만든다.
- **항상 Layer 1이 우선**이고 Layer 2는 gap을 메우는 fallback이다. 다만 알림 문구(사람에게 보여줄 자연어 메시지) 생성은 risk_level과 무관하게 항상 Layer 2(LLM)가 전담한다.
- Layer 2의 모든 판단은 로그(`ai_risk_logs`)에 남긴다 — 이후 "AI가 실제로 어떤 케이스를 어떻게 판단했는지"를 근거로 Layer 1 매트릭스를 확장하는 피드백 루프로 쓸 수 있다. 초기엔 하드코딩 규칙으로 시작해서 운영 데이터로 규칙을 정교화해나가는 과정 자체가 좋은 인터뷰 스토리가 된다.

## 5. FDE 역량 매핑

이 프로젝트의 각 구성 요소가 실제 국내 FDE 채용 공고(센드버드코리아, 채널톡, 하이퍼이지)의 자격/우대 요건 중 무엇을 증명하는지 정리.

| 프로젝트 구성 요소 | 증명하는 역량 | 관련 JD 요건 |
|---|---|---|
| 다중 공공 API 수집·정규화 파이프라인 | 데이터 엔지니어링, ETL | 데이터/백엔드 엔지니어 배경 선호 |
| PostgreSQL 스키마 설계 (지역/인물/구독/이벤트) | DB 모델링 | 필수: SQL/데이터 모델링 |
| FastAPI 백엔드 + JWT 인증 | Python 백엔드, 풀스택 | 필수: Python 능숙, 백엔드 프레임워크 |
| 규칙+AI 하이브리드 위험도 판단 로직 | 비즈니스 로직→엔지니어링 전환, AI 활용 | 문제 정의부터 구현까지 전 주기 수행, LLM API 경험 |
| (확장) LangGraph 기반 알림 우선순위 에이전트 | 에이전틱 워크플로 | 우대: LangChain/LangGraph/CrewAI |
| Docker + GCP Cloud Run 배포, GitHub Actions CI/CD | 클라우드 인프라, DevOps | 우대: AWS/GCP/Azure, CI/CD |
| 웹(PWA) 우선 + FCM 웹푸시/앱푸시 통합 설계 | 접근성 설계, 크로스플랫폼 인프라 판단 | 풀스택 경험, 제품 감각 |
| Flutter 모바일 앱 확장 | 기존 강점 재활용 | 풀스택 경험 |
| 문제 발견 → 설계 → 배포 전 과정 문서화 | 디스커버리 서사 | 이력서 필수 서술 항목 (채널톡) |

### 6-1. 검증: 공공데이터로 국지적 재난(예: 지하차도 침수)을 잡을 수 있나?
2023년 오송 궁평2지하차도 침수 사고를 기준으로 확인해봤다.

- **잡을 수 있었다.** 정부 감찰 자료 기준 사고 지점(미호천교)의 홍수경보는 사고 4시간 17분 전, 제방 붕괴는 18분 전에 발생했다. 이 홍수특보는 한강홍수통제소가 하천 관측소 지점 단위로 발령하는 데이터이고, data.go.kr(3040409)로 무료·실시간 공개돼 있다.
- **단, 기상청 일반 호우특보(시군 단위)만으로는 부족하다.** "오송읍에 비가 많이 온다"까지만 알 수 있고 "이 지하차도가 위험하다"는 알 수 없다. 해상도 차이가 핵심이다.
- **위치 연결이 필요하다.** 홍수특보를 특정 지하차도/교량 위험으로 바꾸려면 하천 관측소와 인프라 지점을 지리적으로 매칭해야 한다. 지하차도 위치 데이터(data.go.kr 15124755)로 이 매칭이 가능하다.
- **한계도 있다.** 제방 붕괴 자체는 부실시공 등 구조적 결함 문제라 수위 데이터만으로 "언제 무너질지"는 예측할 수 없다. 이 프로젝트가 할 수 있는 건 이미 공개된 공식 위험 신호를 더 빠르고 구체적으로 전달하는 것이지, 재해 자체를 예측하는 게 아니다 — 이 한계는 문서/발표에 명시할 것.
- **미확인 사항**: hrfco.go.kr이 4대강(한강·금강·낙동강·영산강) 홍수통제소를 통합 제공하는지, 미호강처럼 금강 수계 관할 지점까지 커버하는지는 실제 API 연동 시 재확인 필요.

## 7. 알림 채널 전략 — 웹 우선 + 웹푸시

목표: 설치 없이 브라우저에서 바로 체험 가능한 **PWA(Progressive Web App)를 먼저 만들어 접근성을 확보**하고, 이후 Flutter 네이티브 앱으로 확장한다. 백엔드 알림 파이프라인은 처음부터 채널에 무관하게 공유되도록 설계해서, 앱을 나중에 추가해도 재작업이 없게 한다.

- **기술 선택: Firebase Cloud Messaging (FCM)** — Web Push, Android, iOS를 하나의 API로 지원. 이미 Firebase를 다뤄본 경험이 있어서 새로 배울 게 적다.
- **웹 (1차, MVP)**: Flutter Web(또는 순수 웹 PWA) + Service Worker 등록 → 브라우저 알림 권한 요청 → FCM 웹 토큰 발급 → 백엔드(`device_tokens`)에 등록 → 이벤트 발생 시 FCM으로 push.
- **앱 (2차, 확장)**: 동일 FCM 파이프라인 위에 Flutter 모바일(Android/iOS) 클라이언트만 추가. 알림 로직·백엔드는 변경 없음.
- **알려진 제약**: iOS Safari 웹푸시는 iOS 16.4 이상에서 "홈 화면에 추가(PWA 설치)"한 경우에만 지원되고, 브라우저 탭에서 바로는 동작하지 않는다. 이 제약은 README/발표자료에 명시하고, 데모는 Android·데스크톱 브라우저 중심으로 진행하는 걸 권장.

## 10. 단계별 로드맵 (MVP → 확장)

**Phase 1 — 데이터 파이프라인 & 백엔드 뼈대**
기상특보 + 지진 + 홍수통제소 수문DB(관측소→관할 시군 매핑) API 연동, PostgreSQL 스키마 구축, FastAPI 기본 CRUD, Docker 로컬 실행

**Phase 2 — 위험도 판단 로직 + 웹 MVP**
Layer1 규칙 매트릭스 구현(홍수특보 지역 단위 알림 포함), Layer2 LLM 보조 판단 붙이기, 웹(PWA) 구독 관리 UI, FCM 웹푸시 연동

**Phase 3 — 배포 & 운영**
GCP Cloud Run 배포, GitHub Actions CI/CD, 기본 모니터링/로깅

**Phase 4 — Flutter 네이티브 앱 확장**
동일 백엔드/FCM 파이프라인 위에 Flutter 모바일(Android/iOS) 클라이언트 추가

**Phase 5 (선택 확장)**
긴급재난문자 소스 추가, 지하차도/교량 위치 정밀 매칭으로 홍수특보를 지점 단위 알림으로 정교화(인프라 지점 알림, 2-1a·6-1절), LangGraph 기반 다중 이벤트 우선순위 에이전트, 지반침하 실시간성 재검증 후 추가 검토, Vector DB로 과거 이벤트 유사도 기반 알림 톤 조정
