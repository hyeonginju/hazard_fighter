## Part 1. 이 프로젝트가 하는 일 (큰 그림)

한 문장으로: **공공데이터(기상특보·지진·홍수 등)를 계속 수집해서, 사용자가 등록한 "인물"의 특성(나이·건강상태 등)에 맞춰 위험한 상황만 골라 알림을 보내는 백엔드.**

예를 들어 "충북 청주 흥덕구에 사는 고령의 어머니"를 등록해두면, 그 지역에 폭염특보가 뜰 때 시스템이 "고령 + 폭염 = 높은 위험"이라고 판단해서 알림을 만든다. 반면 같은 폭염이라도 건강한 성인에겐 위험도를 낮게 매긴다.

### 데이터가 흐르는 순서 (이게 시스템의 핵심)

```
① 수집(Ingestion)        공공 API에서 재난 데이터를 가져온다
        ↓
② 정규화 → events 저장   소스마다 제각각인 데이터를 공통 형식으로 바꿔 DB에 쌓는다
        ↓
③ 구독 매칭              그 지역을 구독한 사용자/인물을 찾는다
        ↓
④ 위험도 평가(Layer 1)   인물 특성 + 이벤트 종류로 LOW/MEDIUM/HIGH를 매긴다
        ↓
⑤ notifications 생성     위험하다고 판단되면 알림 레코드를 만든다
                        (실제 발송은 Phase 2)
```

이 흐름이 코드에서는 `app/services/ingest.py`의 `run_ingestion_cycle()` 함수 하나에 그대로 담겨 있다. 함수를 읽으면 위 5단계가 순서대로 보인다.

### 왜 이렇게 단계를 나눴나 (레이어드 아키텍처)

각 단계를 별도 파일/폴더로 분리했다. "수집"은 `app/ingestion/`, "위험도 판단"은 `app/risk/`, "DB 모델"은 `app/models/`, "외부에 노출하는 API"는 `app/api/` 하는 식이다.

이렇게 나누는 이유는, 나중에 한 부분을 바꿔도 다른 부분이 안 흔들리게 하기 위해서다. 예를 들어 홍수 데이터 API의 응답 형식이 바뀌어도, 고쳐야 할 곳은 `app/ingestion/hrfco_flood.py` 하나뿐이다. 위험도 판단 로직이나 DB는 건드릴 필요가 없다. 이게 "관심사의 분리(separation of concerns)"라는 개념이고, 규모가 커질수록 유지보수를 살린다.

## Part 3. 개념 + 결정 (주제별 학습 가이드)

### 3-1. 웹 백엔드와 REST API, 그리고 FastAPI

💡 **개념.**
"백엔드"는 사용자 눈에 안 보이는 서버 쪽 프로그램이다. 웹/앱 화면(프론트엔드)이 "이 사용자의 인물 목록 줘"라고 요청하면, 백엔드가 DB에서 꺼내 응답한다. 이 요청/응답을 주고받는 규칙을 정해둔 게 **API**이고, 그중 가장 흔한 방식이 **REST**다. REST는 "주소(URL) + 동사(GET/POST 등)"로 자원을 다룬다. 예: `GET /persons`는 "인물 목록 조회", `POST /persons`는 "인물 새로 생성".

- `GET` = 조회 (읽기)
- `POST` = 생성 (쓰기)
- `PUT`/`PATCH` = 수정, `DELETE` = 삭제

🔧 **이 프로젝트에서.**
FastAPI로 API를 만들었다. 엔드포인트(주소별 처리 함수)는 `app/api/routes/` 폴더에 자원별로 나눠 있다 — `persons.py`, `regions.py`, `subscriptions.py`, `events.py`, `notifications.py`, `health.py`. 예를 들어 `app/api/routes/persons.py`를 보면:

```python
@router.post("", response_model=PersonRead)
def create_person(payload: PersonCreateRequest, db: Session = Depends(get_db)):
    ...
```

- `@router.post("")` → 이 함수는 `POST /persons` 요청을 처리한다는 표시(데코레이터)
- `payload: PersonCreateRequest` → 요청 본문(JSON)을 자동으로 검증해서 파이썬 객체로 준다
- `response_model=PersonRead` → 응답 형태를 정해두면 문서에도 자동 반영되고, 불필요한 필드가 새어나가는 걸 막는다
- `db: Session = Depends(get_db)` → "의존성 주입". 요청이 올 때마다 FastAPI가 DB 세션을 알아서 만들어 넣어준다 (3-6에서 설명)

FastAPI를 고른 결정적 이유는 **자동 문서화**다. 서버를 켜고 `http://localhost:8000/docs`에 들어가면, 내가 만든 모든 API가 눌러볼 수 있는 문서로 나온다. 이건 프론트 개발자나 협업자에게 API를 설명할 때 시간을 크게 줄여준다 — FDE처럼 고객사와 붙어 일하는 직무에서 특히 유용하다.

🎤 **면접 한마디.**
"FastAPI를 쓴 이유는 타입 힌트 기반으로 요청/응답 검증과 OpenAPI 문서가 자동 생성돼, 최소한의 코드로 안전한 API를 빠르게 만들 수 있기 때문입니다."

### 3-2. 관계형 데이터베이스와 PostgreSQL

💡 **개념.**
데이터베이스(DB)는 데이터를 저장·조회하는 전용 프로그램이다. "관계형(relational)" DB는 데이터를 **표(table)** 로 저장한다. 엑셀 시트를 떠올리면 된다 — 행(row)은 데이터 하나, 열(column)은 속성.

핵심 개념 3가지:
- **기본키(Primary Key, PK)** — 각 행을 유일하게 구분하는 값. 예: 인물마다 붙는 고유 id.
- **외래키(Foreign Key, FK)** — 다른 표의 행을 가리키는 값. 예: `persons` 표의 각 인물은 `user_id`로 `users` 표의 소유자를 가리킨다. 이걸로 표끼리 "관계"를 맺는다.
- **정규화** — 같은 데이터를 여러 곳에 중복 저장하지 않고 표를 나눠 FK로 잇는 것.

🔧 **이 프로젝트에서.**
PostgreSQL을 골랐다. 표는 총 12개다: `users`, `persons`, `person_tags`, `regions`, `subscriptions`, `device_tokens`, `risk_matrix_rules`, `ai_risk_logs`, `events`, `notifications`, `river_gauges`, `gauge_region_maps`. (`app/models/__init__.py`에 전부 나열돼 있다.)

관계 예시:
- 한 명의 `user`가 여러 `person`을 등록 (1:N)
- 한 `person`은 여러 `person_tag`를 가짐 (예: "고령" + "보행보조필요")
- `subscription`은 어떤 `person`이 어떤 `region`의 알림을 받을지 잇는 연결 표

PostgreSQL을 고른 이유는 **JSONB**와 **배열** 같은 고급 컬럼 타입 때문이다(3-7에서 자세히). 재난 API의 원본 응답을 통째로 보존해야 하는데, 그 형식이 소스마다 다르고 나중에 바뀔 수도 있어서, 정형 컬럼만으로는 부족했다.

🎤 **면접 한마디.**
"원본 API 페이로드처럼 스키마가 유동적인 데이터를 다뤄야 해서, JSONB를 네이티브로 지원하는 PostgreSQL을 골랐습니다. 정형 데이터는 컬럼으로, 비정형 원본은 JSONB로 저장하는 하이브리드 전략을 썼습니다."

### 3-3. ORM과 SQLAlchemy — DB를 파이썬 객체로 다루기

💡 **개념.**
원래 DB와 대화하려면 **SQL**이라는 별도 언어를 써야 한다 (`SELECT * FROM persons WHERE user_id = ...`). **ORM(Object-Relational Mapping)** 은 이 SQL을 대신 써주는 통역사다. 파이썬 클래스로 표를 정의하고, 파이썬 객체를 다루듯 코드를 쓰면 ORM이 SQL로 번역해준다.

🔧 **이 프로젝트에서.**
SQLAlchemy로 각 표를 파이썬 클래스로 정의했다. `app/models/event.py`의 `Event` 클래스가 `events` 표에 대응한다:

```python
class Event(Base):
    __tablename__ = "events"
    id: Mapped[uuid.UUID] = mapped_column(Uuid(as_uuid=True), primary_key=True, default=uuid.uuid4)
    source: Mapped[str] = mapped_column(String(30), nullable=False)
    region_id: Mapped[uuid.UUID | None] = mapped_column(ForeignKey("regions.id"), nullable=True)
    raw_payload: Mapped[dict] = mapped_column(JsonVariant, nullable=False)
    ...
    region: Mapped["Region"] = relationship(back_populates="events")
```

읽는 법:
- `class Event(Base)` → `Base`를 상속하면 SQLAlchemy가 "이건 DB 표"라고 인식
- `mapped_column(...)` → 컬럼 하나. `primary_key=True`면 PK, `ForeignKey("regions.id")`면 FK, `nullable=False`면 필수값
- `default=uuid.uuid4` → 새 행 만들 때 id를 자동 생성
- `relationship(...)` → FK로 이어진 다른 표를 파이썬 속성처럼 접근하게 해줌. `event.region`이라고 쓰면 SQLAlchemy가 알아서 조인해서 지역 객체를 준다

ORM을 쓰면 SQL을 직접 안 짜도 되고, 오타로 인한 실수가 줄고, 파이썬 타입 검사의 도움을 받는다. 대신 복잡한 쿼리는 SQL보다 표현이 어렵거나 성능 튜닝이 필요할 때가 있다 — 이게 ORM의 트레이드오프다.

🎤 **면접 한마디.**
"SQLAlchemy로 표를 파이썬 클래스로 모델링해서, 타입 안정성과 생산성을 얻었습니다. 단순 CRUD는 ORM으로, 복잡한 집계 쿼리는 필요하면 raw SQL로 내려가는 식으로 갈 계획입니다."

### 3-4. 모델 vs 스키마 — 왜 두 벌로 나눴나 (Pydantic)

💡 **개념.**
헷갈리기 쉬운 부분. 이 프로젝트엔 데이터 모양을 정의하는 파일이 두 종류다.
- **모델(model)** — `app/models/`. DB 표의 구조. "데이터가 **저장**되는 형태."
- **스키마(schema)** — `app/schemas/`. API로 주고받는 형태. "데이터가 **오가는** 형태."

🔧 **이 프로젝트에서.**
왜 굳이 나눌까? DB에 저장하는 것과 사용자에게 보여주는 것이 항상 같지 않기 때문이다. 예를 들어 비밀번호 해시는 DB엔 있지만 API 응답엔 절대 나가면 안 된다. 반대로 API 입력엔 있지만 DB엔 가공해서 저장하는 값도 있다.

`app/schemas/person.py`를 보면 입력용/출력용이 나뉘어 있다:

```python
class PersonCreate(BaseModel):     # 입력: 사용자가 보내는 것
    label: str
    age_group: str
    tags: list[str] = []

class PersonRead(BaseModel):       # 출력: 사용자에게 돌려주는 것
    model_config = ConfigDict(from_attributes=True)
    id: uuid.UUID
    label: str
    age_group: str
    created_at: datetime
    tags: list[str] = []
```

이 스키마들은 **Pydantic**으로 만든다. Pydantic은 들어온 데이터가 형식에 맞는지 자동 검증한다 — 예를 들어 `age_group`에 숫자가 오면 자동으로 에러를 낸다. `from_attributes=True`는 "SQLAlchemy 모델 객체를 이 스키마로 자동 변환해도 된다"는 설정이다.

이렇게 나누면 **DB 구조와 API 계약을 독립적으로 바꿀 수 있다.** DB에 컬럼을 추가해도 API 응답은 그대로 유지할 수 있고, 그 반대도 된다.

🎤 **면접 한마디.**
"DB 모델(SQLAlchemy)과 API 스키마(Pydantic)를 분리해서, 저장 구조와 외부 계약을 독립적으로 진화시킬 수 있게 했습니다. 민감 필드 노출도 스키마 레벨에서 통제됩니다."

### 3-5. 마이그레이션과 Alembic — DB 구조를 버전 관리하기

💡 **개념.**
코드는 Git으로 버전 관리한다. 그런데 DB의 **구조(표·컬럼)** 도 시간이 지나면 바뀐다 — 컬럼 추가, 표 신설 등. 이 변경 이력을 코드처럼 관리하는 게 **마이그레이션**이다. 각 변경을 파일로 남겨두면, 어느 컴퓨터에서든 "이 순서대로 실행"만 하면 똑같은 DB 구조를 재현할 수 있다.

🔧 **이 프로젝트에서.**
Alembic으로 관리한다. 첫 마이그레이션은 `migrations/versions/0001_initial_schema.py`다. 명령어 흐름:
- `alembic upgrade head` → 최신 구조까지 DB에 반영
- `alembic revision --autogenerate -m "설명"` → 모델을 바꾼 뒤 변경분을 자동으로 마이그레이션 파일로 뽑기

📝 한 가지 특이점(솔직한 기록): 이 스캐폴딩을 처음 만든 환경에선 로컬에 Postgres를 못 띄웠다. 그래서 `alembic revision --autogenerate`를 실제 DB에 못 돌려봤고, 대신 첫 마이그레이션을 `Base.metadata.create_all()`을 직접 호출하는 방식으로 작성했다. 나중에 실제 Postgres를 띄운 뒤부터는 정석대로 `--autogenerate`로 새 리비전을 만들면 된다.

⚠️ **그리고 그 선택이 2026-07-27 배포 첫 순간에 터졌다 (핵심 교훈).**
클라우드 DB(Neon)에 처음 `alembic upgrade head` 를 돌리자 이렇게 죽었다 — `column "auth_provider" of relation "users" already exists`. 원인은 한 문장으로 요약된다: **`create_all()` 은 "이 리비전 시점의 스키마"가 아니라 "지금 이 순간의 모델 전체"를 만든다.** 0002(users 소셜 컬럼)·0003(ingest_runs)이 생긴 뒤에는 빈 DB 에서 0001 이 이미 그 컬럼까지 다 만들어버리고, 뒤이어 0002 가 "이미 있다"며 실패한다.

**왜 반년 가까이 안 드러났나.** 기존 DB(로컬 Postgres)는 리비전을 하나씩 순서대로 밟아왔기 때문이다. **"기존 DB 를 업그레이드하는 경로"만 매일 테스트되고 "빈 DB 를 처음부터 만드는 경로"는 한 번도 테스트되지 않았다.** 그런데 배포는 정확히 후자다. 오늘 아침에 고친 테스트 시간 폭탄(절대 날짜를 박아둬 48시간 창을 벗어나자 깨진 것)과 **같은 모양의 버그**다 — 고정 스냅샷이어야 할 것이 현재 상태를 참조하고 있었다.

**고친 방법.** 0001 을 그 시점 스키마(테이블 12개, users 는 email 필수·소셜 컬럼 없음)의 **명시적 `op.create_table` DDL** 로 다시 썼다. 이제 0001 은 모델이 아무리 변해도 흔들리지 않는다.

**고쳤다고 믿지 않고 검증했다.** 빈 DB 에 0001→0002→0003 을 재생한 뒤, 결과 스키마를 `Base.metadata` 와 대조하는 스크립트(`scripts/verify_schema.py`)를 만들어 돌렸다. 첫 실행에서 **불일치 7건**이 나왔다 — 내가 새로 쓴 0001 의 `created_at` 들이 `nullable=False` 를 빠뜨려 모델(NOT NULL)과 달랐다. 실무상 피해는 거의 없는 차이(server_default 가 있으니 항상 값이 들어간다)지만, **"경로를 다 밟았는데 다른 곳에 도착했다"는 사실 자체가 문제**다. 고치고 다시 재생해 "일치 ✅"를 확인했다. 원칙: **모델이 진실이고 마이그레이션은 그 진실에 도달하는 경로다. 경로의 도착지를 기계로 대조하라.**

🎤 **면접 한마디.**
"Alembic으로 스키마 변경을 버전 관리해서, 환경 간 DB 구조를 재현 가능하게 만들었습니다. 초기 마이그레이션을 `create_all()` 로 작성한 편의적 선택이 '빈 DB 에서 처음부터 적용하는 경로'를 깨뜨린다는 걸 실제 배포에서 발견하고, 그 시점 스냅샷의 명시적 DDL 로 고정했습니다. 그리고 고쳤다는 걸 믿지 않고 마이그레이션 결과와 모델을 대조하는 검증 스크립트를 만들어 nullable 불일치 7건을 추가로 잡았습니다 — 업그레이드 경로만 매일 테스트되고 신규 생성 경로는 한 번도 테스트되지 않았다는 게 근본 원인이었습니다."

### 3-6. 세션·트랜잭션·commit — DB에 안전하게 쓰기

💡 **개념.**
DB에 여러 변경을 할 때, "전부 성공 아니면 전부 취소"를 보장해야 할 때가 있다. 예: 인물을 만들고 태그 3개를 다는데, 중간에 실패하면 반쪽짜리 인물이 남으면 안 된다. 이 "전부 아니면 전무" 묶음이 **트랜잭션(transaction)** 이다.
- **세션(session)** — DB와의 대화 창구. 변경사항을 임시로 모아둔다.
- **commit** — 모아둔 변경을 실제로 DB에 확정.
- **flush** — DB에 보내되 아직 확정(commit) 전. 방금 만든 행의 id 같은 걸 미리 얻을 때 쓴다.
- **rollback** — 확정 전 변경을 전부 취소.

🔧 **이 프로젝트에서.**
`app/database.py`에서 세션 공장을 만들고, `get_db()`가 요청마다 세션을 열고 끝나면 닫는다:

```python
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

`flush`와 `commit`의 차이가 실제로 쓰인 예가 `app/crud.py`의 `create_person`이다:

```python
def create_person(db, user, label, age_group, tags):
    person = Person(user_id=user.id, label=label, age_group=age_group)
    db.add(person)
    db.flush()          # ← 아직 확정 전이지만 person.id를 얻으려고 flush
    for tag in tags:
        db.add(PersonTag(person_id=person.id, tag=tag))   # 그 id로 태그 연결
    db.commit()         # ← 인물 + 태그를 한 번에 확정
    db.refresh(person)
    return person
```

여기서 `flush()`로 person.id를 먼저 확보하고, 그 id로 태그들을 붙인 다음, 마지막에 `commit()` 한 번으로 인물과 태그를 함께 확정한다. 중간에 실패하면 인물도 태그도 저장되지 않는다.

🎤 **면접 한마디.**
"연관 데이터를 하나의 트랜잭션으로 묶어 정합성을 보장했습니다. flush로 부모 행의 PK를 얻고, 자식 행을 붙인 뒤 commit으로 원자적으로 확정하는 패턴을 썼습니다."

### 3-7. ⭐ 다이얼렉트 호환 타입 — 이 프로젝트의 핵심 트릭

이건 이번 세션에서 실제로 리팩터링한 부분이라 특히 자세히 남긴다. FDE 면접에서 "실전 문제를 어떻게 풀었나" 사례로 쓰기 좋다.

💡 **개념.**
DB마다 지원하는 데이터 타입이 조금씩 다르다. 이 방언 차이를 SQLAlchemy에선 **다이얼렉트(dialect)** 라고 부른다. PostgreSQL엔 있는 특수 타입이 SQLite엔 없다:
- **UUID** — 전 세계에서 겹치지 않는 긴 고유 id (예: `550e8400-e29b-...`). Postgres는 네이티브 지원, SQLite는 없음.
- **JSONB** — JSON을 효율적으로 저장/검색하는 Postgres 전용 타입.
- **ARRAY** — 한 컬럼에 값 여러 개(배열)를 넣는 Postgres 기능.

🔧 **문제 상황.**
운영 DB는 PostgreSQL을 쓰기로 했다. 그런데 **테스트를 돌릴 때마다 Postgres 서버를 띄우는 건 무겁고 느리다.** 테스트는 가볍고 빠른 SQLite(파일/메모리 기반 DB)로 돌리고 싶었다. 문제는, 모델에 Postgres 전용 타입(JSONB, ARRAY)을 그대로 박아두면 SQLite에선 그 타입을 몰라서 테스트가 아예 안 돌아간다.

🔧 **해결.**
"Postgres에선 네이티브 타입, 그 외 DB에선 표준 타입"으로 자동 전환되는 컬럼 타입을 만들었다. `app/models/types.py`:

```python
from sqlalchemy import JSON, String, Uuid
from sqlalchemy.dialects.postgresql import ARRAY, JSONB

# JSONB on Postgres, JSON elsewhere
JsonVariant = JSON().with_variant(JSONB, "postgresql")

# text[] on Postgres, JSON list elsewhere
StringArrayVariant = JSON().with_variant(ARRAY(String), "postgresql")
```

핵심은 `.with_variant(...)`다. "기본은 표준 JSON을 쓰되, 다이얼렉트가 'postgresql'이면 JSONB로 바꿔라"는 뜻이다. UUID는 SQLAlchemy 2.0의 `Uuid` 타입이 이미 이 전환을 알아서 해준다(Postgres UUID ↔ 그 외 CHAR(32)).

이렇게 하니 **모델 정의는 한 벌인데, 운영에선 Postgres의 성능을, 테스트에선 SQLite의 가벼움을** 둘 다 얻었다. `app/models/event.py`에서 이 타입들을 이렇게 쓴다:

```python
raw_payload: Mapped[dict] = mapped_column(JsonVariant, nullable=False)
news_refs: Mapped[list[str] | None] = mapped_column(StringArrayVariant, nullable=True)
```

이 리팩터 덕분에 DB 서버 없이도 "실제 DB에 저장했다가 다시 읽는" 통합 테스트(3-10)가 가능해졌다.

🎤 **면접 한마디.**
"운영은 PostgreSQL, 테스트는 SQLite로 돌리기 위해 SQLAlchemy의 with_variant로 다이얼렉트별 컬럼 타입을 분기했습니다. 모델 정의는 단일 소스로 유지하면서, 운영 성능과 테스트 속도를 동시에 얻은 결정입니다."

### 3-8. 설정과 시크릿 관리 — .env와 pydantic-settings

💡 **개념.**
API 키·DB 비밀번호 같은 **비밀값(시크릿)** 은 코드에 직접 적으면 안 된다. Git에 올라가면 유출되니까. 대신 `.env` 파일에 따로 두고, 프로그램이 실행될 때 읽어온다. `.env`는 `.gitignore`로 Git에서 제외한다.

🔧 **이 프로젝트에서.**
`app/config.py`에서 pydantic-settings로 `.env`를 읽는다:

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    database_url: str = "postgresql+psycopg2://hazard:hazard@localhost:5432/hazard_fighter"
    kma_warning_api_key: str | None = None
    ...

@lru_cache
def get_settings() -> Settings:
    return Settings()
```

- `env_file=".env"` → `.env`에서 값을 읽음
- 키가 없으면 `None`이 기본값 → 키 없이도 프로그램이 죽지 않고 mock 모드로 동작(3-9)
- `@lru_cache` → 설정을 한 번만 읽고 재사용(매번 파일 읽기 방지)

**시크릿 관리 규칙(이번 세션에서 정립):**
- `.env` = 실제 키. `.gitignore`됨 → 커밋 안 됨
- `.env.example` = 빈 템플릿. 커밋됨 → "이런 변수가 필요하다"는 안내용
- `secrets/` = Firebase 서비스 계정 JSON 등. `.gitignore`됨

📝 이번 세션에 실제로 사고가 있었다: 처음에 `.env.example`(=커밋되는 파일)에 실제 키를 적어버렸다. 이걸 발견하고 (1) 실제 값은 `.env`로 옮기고 (2) `.env.example`은 빈 템플릿으로 되돌리고 (3) `secrets/`를 `.gitignore`에 추가하고 (4) 이미 커밋에 박힌 키는 `git filter-repo`로 히스토리에서 스크럽했다. 자세한 건 3-13.

🎤 **면접 한마디.**
"시크릿은 .env로 분리하고 pydantic-settings로 타입 검증과 함께 로드합니다. 커밋되는 .env.example은 값 없는 템플릿으로만 유지해, 실수로 키가 유출되지 않게 했습니다."

### 3-9. 외부 API 연동과 mock fallback 패턴

💡 **개념.**
외부 API(여기선 공공데이터 포털)에 의존하는 코드는, 그 API 없이는 개발/테스트가 막히기 쉽다. 키 발급이 며칠 걸리거나, 호출 한도가 있거나, 응답이 느릴 수 있다. 이럴 때 쓰는 게 **mock(가짜 데이터)** 이다 — 실제 API 대신 미리 만들어둔 응답을 돌려준다.

🔧 **이 프로젝트에서.**
`app/ingestion/base.py`에 **추상 클래스**로 공통 규칙을 정했다:

```python
class BaseIngestionClient(ABC):
    def fetch(self) -> list[NormalizedEvent]:
        if not self.api_key:
            return self._fetch_mock()   # 키 없으면 가짜 데이터
        return self._fetch_live()       # 키 있으면 진짜 호출

    @abstractmethod
    def _fetch_mock(self): ...
    @abstractmethod
    def _fetch_live(self): ...
```

- **추상 클래스(ABC)** = "이걸 상속하는 애들은 반드시 `_fetch_mock`과 `_fetch_live`를 구현해야 한다"는 계약. 각 소스(`kma_warnings.py`, `kma_earthquake.py`, `hrfco_flood.py`)가 이걸 상속해 자기 방식으로 구현한다.
- `fetch()`의 스위치 하나로, **키가 있으면 실제, 없으면 mock** 으로 자동 전환. 그래서 키 발급을 기다리는 동안에도 DB·위험도·API를 전부 개발·테스트할 수 있었다.

또 하나 중요한 설계: 소스마다 응답 형식이 다르니, 전부 `NormalizedEvent`라는 **공통 형식**으로 변환한 뒤에 저장한다. 이렇게 하면 뒷단(위험도 판단 등)은 "어느 소스에서 왔는지" 신경 안 써도 된다. 이게 3-1에서 말한 관심사의 분리다.

🎤 **면접 한마디.**
"외부 API 클라이언트를 추상 클래스로 통일하고, 키 유무에 따라 live/mock을 자동 전환하게 했습니다. 덕분에 키 발급 지연과 무관하게 파이프라인 전체를 개발·테스트할 수 있었고, 모든 소스를 공통 스키마로 정규화해 하위 로직을 소스에 독립적으로 유지했습니다."

### 3-10. 위험도 판단 로직 — 규칙 매트릭스(Layer 1)와 LLM(Layer 2)

💡 **개념.**
"이 상황이 이 사람에게 얼마나 위험한가"를 판단하는 방법은 크게 둘이다.
- **결정론적 규칙(rule-based)** — "폭염 + 고령 = HIGH"처럼 미리 정한 표(매트릭스)대로 판단. 빠르고, 결과가 항상 같고(예측 가능), 테스트하기 쉽다. 대신 표에 없는 경우는 못 잡는다.
- **LLM 기반** — AI에게 상황을 설명하고 판단을 맡김. 유연하지만 느리고, 비용이 들고, 결과가 매번 달라질 수 있다.

🔧 **이 프로젝트에서.**
두 개를 계층으로 나눴다(spec 4절). **Layer 1은 규칙 매트릭스**로 먼저 판단하고, 규칙에 안 걸리는 애매한 경우만 **Layer 2 LLM**으로 넘긴다(Layer 2는 Phase 2 예정).

Layer 1은 `app/risk/matrix.py`에 있다. 규칙을 파이썬 리스트로 하드코딩했다:

```python
RISK_MATRIX = [
    {"event_type": EventType.HEATWAVE, "severity": None, "trigger_type": "age_group",
     "trigger_value": AgeGroup.SENIOR, "risk_level": RiskLevel.HIGH},
    # 폭염 + 고령 = HIGH
    ...
]
```

판단 함수 `evaluate_risk()`는 이벤트 종류·인물 나이대·태그·특보 등급을 받아서, 매칭되는 규칙 중 **가장 높은 위험도**를 돌려준다. 매칭이 하나도 없으면 `None`을 돌려주는데, 이 `None`이 바로 "Layer 2로 넘겨야 할 케이스"라는 신호다. 지진은 등급 문자열이 아니라 규모(숫자)가 기준이라 `evaluate_earthquake_risk()`로 따로 처리한다(4.0 이상 HIGH 등).

📝 설계 노트: 같은 규칙을 `risk_matrix` **테이블**에도 미러링해두는 코드(`scripts/seed_risk_matrix.py`)가 있지만, 지금 `evaluate_risk()`는 그 테이블을 읽지 않고 코드의 리스트를 쓴다. 테이블 버전은 나중에 "관리자 화면에서 규칙 조정" 같은 확장과 감사(audit)를 위한 사전 포석이다. MVP에선 코드 하드코딩이 정확성·테스트에 유리해서 그렇게 갔다.

🎤 **면접 한마디.**
"위험도 판단을 2계층으로 설계했습니다. 명확한 케이스는 결정론적 규칙 매트릭스로 빠르고 재현 가능하게 처리하고, 규칙이 못 잡는 애매한 케이스만 LLM으로 폴백합니다. 비용·지연·예측가능성의 균형을 맞춘 결정입니다."

### 3-11. 테스트 — pytest와 SQLite 인메모리 E2E

💡 **개념.**
테스트는 "코드가 의도대로 도는지"를 자동으로 확인하는 코드다. 한 번 짜두면, 나중에 코드를 고쳤을 때 뭔가 깨졌는지 즉시 알 수 있다. 종류:
- **단위 테스트** — 함수 하나를 콕 집어 검증 (예: `evaluate_risk`가 폭염+고령에 HIGH를 내는지)
- **통합/E2E 테스트** — 여러 부분을 이어서 "전체 흐름"을 검증 (예: 이벤트가 들어와 알림이 생기기까지)

🔧 **이 프로젝트에서.**
pytest로 짰고, 테스트는 `tests/` 폴더에 있다:
- `test_risk_matrix.py` — Layer 1 규칙 로직 (단위)
- `test_ingestion.py` — 키 없을 때 mock으로 잘 빠지는지
- `test_pipeline_e2e.py` — **전체 흐름**: 사용자/인물/지역/구독 생성 → ingest → events 저장 → 위험도 평가 → notifications 생성까지
- `test_health.py` — 헬스체크 엔드포인트

핵심은 **이 테스트가 DB 서버 없이 전부 돈다**는 점이다. 3-7의 다이얼렉트 호환 타입 덕분에, 테스트는 메모리 위의 SQLite로 실제 DB 왕복(저장→조회)까지 검증한다. 예: "충북 청주 흥덕구 + 고령 구독자"에 홍수경보 mock을 넣으면 HIGH 알림이 실제로 DB에 생기는지까지 확인한다. 총 19개 테스트가 통과 상태다.

🎤 **면접 한마디.**
"파이프라인 전체를 SQLite 인메모리로 E2E 검증했습니다. 다이얼렉트 호환 타입 덕에 DB 서버 없이도 실제 저장·조회를 포함한 통합 테스트가 가능해, CI에서 빠르게 돌릴 수 있는 구조입니다."

### 3-12. 컨테이너와 Docker — "내 컴퓨터에선 되는데" 없애기

💡 **개념.**
프로그램을 돌리려면 특정 버전의 파이썬, DB, 라이브러리가 필요하다. 사람마다 컴퓨터 환경이 달라서 "내 컴퓨터에선 되는데 네 컴퓨터에선 안 돼" 문제가 생긴다. **Docker**는 앱과 그 실행 환경을 통째로 **컨테이너**라는 상자에 담아, 어디서든 똑같이 돌게 한다. **docker-compose**는 여러 컨테이너(예: 앱 + DB)를 한 번에 정의·실행하는 도구다.

🔧 **이 프로젝트에서.**
`docker-compose.yml`에 두 컨테이너를 정의했다:
- `db` — PostgreSQL 16. 데이터를 `volume`에 저장해 컨테이너를 지워도 데이터가 남게 했고, `healthcheck`로 DB가 진짜 준비됐는지 확인한다.
- `app` — FastAPI 앱. `depends_on`으로 **DB가 건강해진 뒤에** 뜨도록 순서를 잡았다.

`docker compose up -d db` 하나면 팀 누구나 동일한 Postgres를 띄울 수 있다. FDE처럼 여러 환경(내 노트북, 고객사 서버 등)에 배포해야 하는 직무에서 컨테이너는 사실상 필수 소양이다.

🎤 **면접 한마디.**
"앱과 Postgres를 docker-compose로 묶고, healthcheck와 depends_on으로 기동 순서를 보장했습니다. 환경 재현성을 확보해, 온보딩과 배포의 마찰을 줄이는 게 목적이었습니다."

### 3-13. Git 시크릿 위생 — 히스토리 스크럽

💡 **개념.**
Git은 파일의 **모든 변경 이력**을 저장한다. 그래서 실수로 비밀 키를 커밋했다가 나중에 지워도, **과거 커밋 히스토리엔 그대로 남는다.** 최신 파일에서 지운다고 끝이 아니다. 히스토리에서 완전히 없애려면 이력을 다시 쓰는(rewrite) 특수 작업이 필요하다.

🔧 **이 프로젝트에서.**
초기에 `.env.example`에 실제 키(기상청·홍수통제소)가 잠깐 커밋된 적이 있었다. 다행히 원격 저장소에 올리기 전이라 유출은 아니었지만, 안전하게 가려고 히스토리에서 지웠다.

`git filter-repo`라는 도구로, 히스토리 전체를 훑어 특정 문자열을 치환했다. 치환 규칙 파일(`.secret-replacements.txt`)에 "실제 키 → `__REMOVED__`"를 적고:

```bash
git filter-repo --replace-text .secret-replacements.txt --force
```

실행 후, 모든 커밋에서 실제 키가 사라지고 `__REMOVED_KMA_KEY__` 같은 마커만 남은 걸 확인했다. 관련 커밋 해시도 새로 만들어졌다(히스토리를 다시 썼으니 당연). 로컬 전용이었어서 키 재발급은 불필요했다.

📝 교훈: 키는 처음부터 `.env`(gitignore됨)에만 넣는다. `.env.example`엔 절대 실제 값 금지. 커밋 전 `git status`로 `.env`/`secrets/`가 안 딸려가는지 확인.

🎤 **면접 한마디.**
"커밋 히스토리에 남은 시크릿을 git filter-repo로 스크럽하고, .env/.env.example/secrets 구조를 정비했습니다. 지운 게 아니라 이력에서 제거해야 한다는 점을 실제로 처리한 경험입니다."

### 3-14. 백그라운드 작업과 스케줄러 — asyncio와 lifespan

💡 **개념.**
웹 서버는 기본적으로 "요청이 오면 응답한다"는 수동적 존재다. 그런데 우리 서비스는 요청이 없어도 10분마다 알아서 데이터를 수집해야 한다. 이런 걸 **백그라운드 작업**이라고 한다. 파이썬에서는 **asyncio**(비동기 실행 프레임워크)로 "서버가 응답하는 동안 옆에서 따로 도는 루프"를 만들 수 있다. 핵심 개념 세 가지:
- **이벤트 루프** — asyncio의 심장. 여러 작업을 번갈아 실행하는 관제탑.
- **lifespan** — FastAPI가 제공하는 "서버 시작할 때/끝날 때" 훅. 여기서 백그라운드 작업을 켜고 끈다.
- **`asyncio.to_thread`** — 동기(sync) 코드를 이벤트 루프 밖 스레드에서 돌리는 도구. 동기 코드를 루프 안에서 직접 돌리면 그동안 서버가 응답을 못 하게 되기 때문.

🔧 **이 프로젝트에서.**
`app/scheduler.py`의 `ingest_loop()`가 10분마다 수집을 실행하는 무한 루프고, `app/main.py`의 lifespan에서 `asyncio.create_task()`로 띄운다. 우리 ingestion 코드는 동기(httpx 동기 클라이언트)라 `asyncio.to_thread`로 감쌌다.

선택의 이유: **APScheduler 같은 스케줄러 라이브러리를 일부러 안 썼다.** 단일 프로세스 MVP에선 asyncio 표준 기능만으로 충분하고, 의존성 하나가 줄어든다. 대신 퇴로를 설계했다 — 나중에 서버를 여러 대 띄우면 내장 루프가 서로 중복 수집할 수 있으니, 그땐 `SCHEDULER_ENABLED=0`으로 끄고 외부 스케줄러(Cloud Scheduler가 `POST /events/ingest` 호출)로 전환한다. 루프는 어떤 예외에도 죽지 않게 try/except로 감쌌다 — 백그라운드 루프가 소리 없이 죽는 게 최악의 장애 유형이라서다.

**이 "중복 수집"이 왜 심각한지는 3-15(호출량 예산)와 붙여 봐야 보인다** (2026-07-27 배포 준비 중 명시적으로 연결한 내용). 인프로세스 루프에서는 **시계의 개수 = 프로세스의 개수**이므로, 하루 144사이클로 계산한 예산이 인스턴스 수만큼 곱해진다 — 재난문자는 14.4% → 43%(3인스턴스)로 뛴다. 즉 **확장이 곧 한도 초과가 되는 구조**다. 게다가 그걸 막아야 할 중복 가드의 상태가 프로세스 메모리(모듈 전역 변수)라 인스턴스끼리 서로를 못 봐서 조용히 무력해진다 — LLM 쿨다운에 대해 적어둔 "다중 인스턴스면 Redis 등으로 옮겨야 한다"는 한계가 이 가드에도 똑같이 적용된다는 걸 배포를 준비하며 뒤늦게 인식했다. 그래서 07-27에 가드 상태를 `ingest_runs` 테이블로 옮겼다(3-25).

**"무방비 엔드포인트"의 의미도 배포 전후로 달라진다.** 07-20 일지에도 `POST /events/ingest`를 "무방비"라고 적었지만, 그때의 위협은 **내가 실수로 연타하는 것**이었고 그래서 해법이 시간 가드였다. 공개 배포에서의 위협은 **주소를 아는 타인이 고의로 반복 호출해 우리 쿼터와 LLM 비용을 태우는 것**이고, 시간 가드는 낭비를 줄일 뿐 인증이 아니다. 같은 표현이 가리키는 문제가 조건 변화로 바뀐 사례 (07-27에 토큰 인증 추가, 3-25).

🎤 **면접 한마디.**
"단일 프로세스 MVP라 asyncio 백그라운드 태스크로 최소 구성했고, 수평 확장 시 외부 스케줄러로 전환하는 퇴로를 함께 설계했습니다. 동기 수집 코드는 to_thread로 격리해 이벤트 루프 블로킹을 막았습니다. 배포를 준비할 때는 이 코드가 깔고 있던 가정(인스턴스는 하나, 호출자는 나뿐)을 명시적으로 꺼내 검사했고, 각각을 가드 상태의 DB 이전과 엔드포인트 토큰 인증으로 해소했습니다."

### 3-15. 외부 API 호출량 예산 — 한도로부터 설계하기

💡 **개념.**
무료 공공 API에는 호출 한도(quota)가 있다: 일일 최대 호출 수, 분당 최대 호출 수 등. 한도를 넘으면 에러가 나거나 심하면 **키가 차단**된다. 그래서 외부 API에 의존하는 시스템은 "우리가 하루에 몇 번 호출하게 되나"를 미리 계산해야 한다 — 이걸 **호출량 예산(call budget)**이라고 부르자. 폴링 주기 결정의 공식은 단순하다: `일일 호출 수 = (하루 분수 ÷ 폴링 주기 분) × 사이클당 호출 수`.

🔧 **이 프로젝트에서.**
소스별 한도를 조사해 표로 만들었다(Part 4의 2026-07-20 항목). 결론 세 가지가 설계를 결정했다:
- **아키텍처 덕분에 사용자 수와 호출량이 무관하다.** 서버가 소스당 1회 폴링하고 사용자에겐 DB에서 나눠주기(팬아웃) 때문. 폴링 구조의 숨은 장점.
- **가장 빡빡한 소스(재난문자 1,000/일)가 폴링 주기의 상한을 정한다.** 10분 주기 = 144회/일 = 14.4%로 안전, 1분 주기로 당기면 초과. "제일 약한 고리에 맞춘다."
- **낭비 호출을 구조적으로 차단한다.** 수동 ingest 연타 방지 가드(3-14), LLM 쿨다운(3-16), Layer 2 판단 캐시 — 전부 "상태를 기억해서 불필요한 외부 호출을 막는" 같은 패턴의 변주다.

**예산에는 숨은 곱셈 항이 하나 더 있었다 (2026-07-27에 추가).** 위 공식은 프로세스가 하나라는 가정 위에 있다. 주기 실행이 앱 프로세스 안에 있으면 **호출량 = 예산 × 인스턴스 수**가 되므로, 배포에서 인스턴스를 늘리는 것과 예산을 지키는 것이 정면으로 충돌한다. 그래서 "시계를 앱 밖으로 빼는"(외부 cron) 결정은 인프라 취향 문제가 아니라 **예산을 인스턴스 수로부터 독립시키는 설계**다 — 예산 이야기와 스케줄러 이야기가 여기서 하나로 만난다(3-25).

🎤 **면접 한마디.**
"폴링 주기를 감으로 정하지 않고 소스별 한도를 조사해 호출량 예산을 계산했습니다. 예산이 가장 빡빡한 소스가 주기의 상한을 정하고, 가드·쿨다운·캐시로 낭비 호출을 구조적으로 차단했습니다. 배포 단계에서는 예산에 '인스턴스 수'라는 곱셈 항이 숨어 있다는 걸 발견해, 주기 실행을 앱 밖으로 빼서 호출량을 인스턴스 수로부터 분리했습니다."

### 3-16. LLM을 서비스에 안전하게 넣기 — 폴백 체인, 가드레일, 하이브리드

💡 **개념.**
LLM은 강력하지만 서비스 부품으로 보면 불안정하다: 외부 API라 죽을 수 있고, 유료라 quota가 떨어질 수 있고, 출력 형식을 안 지킬 수 있고, 호출마다 돈과 시간이 든다. 그래서 LLM을 프로덕션에 넣을 때의 원칙은 **"LLM이 없어도 서비스가 돌아가야 한다"**이다. 도구 상자:
- **폴백 체인** — 1순위 실패 시 2순위, 최종적으로 LLM 없는 기본 동작.
- **서킷 브레이커/쿨다운** — 죽은 프로바이더에 반복 호출하지 않게 일정 시간 격리.
- **구조화 출력 + 검증** — "첫 줄에 HIGH/MEDIUM/LOW"처럼 형식을 강제하고, 파싱 실패 시 그 응답을 버린다. LLM 출력은 항상 검증 후 사용.
- **하이브리드(규칙 + LLM)** — 명확한 케이스는 결정론적 규칙으로(빠르고 예측 가능·무료), 애매한 케이스만 LLM으로.

🔧 **이 프로젝트에서.**
이 도구들이 전부 실제로 쓰였다. 문구 생성(`message.py`)과 위험도 판단(`risk_ai.py`)이 범용 체인(`llm.py`)을 공유한다: OpenAI → Gemini 무료 → (문구는 템플릿 / 판단은 보류). 401/402/429는 15분 쿨다운. Layer 2는 "첫 줄 레벨" 형식을 강제하고 정규식으로 검증하며, 형식 위반이면 **판단 보류** — 임의로 HIGH(오탐)도 LOW(미탐)도 찍지 않는다. 같은 프로필 조합은 캐시로 재사용해 호출을 아끼고, 모든 판단은 `ai_risk_logs`에 근거와 함께 남긴다. 실증: 경북 의성에서 폭염은 `matrix`가, 호우는 `ai`가 판단한 알림이 한 목록에 나란히 찍혔다(Part 4 참고).

🎤 **면접 한마디.**
"LLM을 신뢰성 요건 안에 가뒀습니다 — 규칙 우선 하이브리드, 3단계 폴백, 쿨다운 격리, 출력 검증과 판단 보류, 프로필 캐시, 전 판단 감사 로그. LLM이 전부 죽어도 서비스는 완전하게 동작합니다."

### 3-17. 로그도 유출 채널이다 — 시크릿 마스킹

💡 **개념.**
시크릿 유출 경로는 코드 저장소만이 아니다. **로그**에도 키가 찍힌다 — 특히 HTTP 클라이언트 라이브러리는 요청 URL 전체를 로깅하는 경우가 많은데, 많은 API가 키를 URL(쿼리스트링이나 경로)에 넣게 한다. 로컬에선 무해해 보여도, 배포 후 로그가 수집 시스템(CloudWatch 등)에 쌓이면 "로그 읽을 권한 = 키 훔칠 권한"이 된다. 파이썬 로깅에는 **필터(Filter)**라는 장치가 있어, 로그가 출력되기 직전에 내용을 검사·수정할 수 있다.

🔧 **이 프로젝트에서.**
스케줄러 검증 중 httpx 로그에 `serviceKey=실제키`가 그대로 찍히는 걸 발견했다. 로그를 꺼버리는 대신(요청 로그는 디버깅에 유용하니까) `app/logging_utils.py`의 `SecretRedactionFilter`를 루트 로거 핸들러에 달아, 설정에 있는 모든 시크릿 값을 `***REDACTED***`로 치환한다. httpx 같은 서드파티 로거는 루트로 전파(propagate)되므로 필터 하나로 전부 커버된다. 오탐 방지로 8자 미만 값은 제외.

🎤 **면접 한마디.**
"시크릿 유출 채널을 저장소 밖 로그까지 넓혀서 봤습니다. 서드파티 로그에 키가 노출되는 걸 발견하고, 로그를 죽이는 대신 루트 로거 필터로 알려진 시크릿만 자동 마스킹해 관측성과 보안을 둘 다 지켰습니다."

### 3-18. 상류를 신뢰하기 + 안전 편향 필터 — 긴급재난문자를 다르게 다룬 이유

💡 **개념.**
데이터 소스를 통합할 때, 모든 소스를 똑같이 다룰 필요는 없다. 어떤 소스는 **원시 신호**(센서값·특보 코드)라 우리가 해석·판정해야 하고, 어떤 소스는 **이미 사람이 판단을 끝낸 결과물**이다. 후자를 우리가 다시 판정하는 건 중복일 뿐 아니라, 상류가 가진 맥락(현장 판단)을 오히려 깎아먹을 수 있다. "상류에서 이미 내린 판단은 다시 내리지 말고 신뢰하라"는 통합 설계의 한 원칙이다.

또 하나: **필터를 화이트리스트로 짤지 denylist로 짤지**는 "무엇을 놓치면 더 위험한가"로 정한다. 화이트리스트(허용 목록)는 목록에 없는 걸 전부 버리므로 **모르는 신규 항목을 놓친다(false negative)**. denylist(차단 목록)는 알려진 나쁜 것만 버리고 나머지는 통과시키므로 **모르는 신규 항목을 살린다**. 안전 시스템에선 대개 "놓치는 것(미탐)"이 "노이즈가 새는 것(오탐)"보다 치명적이라 denylist가 맞을 때가 많다.

🔧 **이 프로젝트에서.**
긴급재난문자(`app/ingestion/safety_disaster.py`)에 두 원칙을 다 적용했다.
- **상류 신뢰(Option A).** 기상특보·지진은 우리가 위험도를 판정하지만, 재난문자는 당국이 이미 "이 지역에 방송할 가치가 있다"고 판정한 완성 경보다. 그래서 위험엔진(규칙/LLM)으로 재판정하지 않고, 필터 통과 = 관련 있음으로 보고 `risk_source=broadcast`/MEDIUM을 매긴다. 개인화는 위험도가 아니라 **문구**에서 한다 — 당국 원문(`MSG_CN`)을 기존 문구생성 LLM이 인물 특성에 맞춰 다듬는다. 덤으로 (a) 폭염/호우가 기상특보와 중복 알림 나는 것과 (b) Layer 2 캐시가 event_type='긴급재난문자'로 뭉개져 서로 다른 문자끼리 충돌하는 버그를 둘 다 피했다.
- **denylist 필터.** `DST_SE_NM`(재난구분)에서 알려진 비재해(`기타`=실종자·물놀이안내, `교통통제`)만 제외한다. 화이트리스트로 짰다면 오늘치 실데이터에 섞인 `산사태·화재·붕괴·홍수`를 일일이 등록해야 했고 하나만 빠뜨려도 놓쳤을 것. denylist라 신규 재해가 자동 통과했다.

🎤 **면접 한마디.**
"소스를 원시 신호와 '이미 판정된 결과물'로 구분해서, 후자(재난문자)는 재판정하지 않고 상류 판단을 신뢰하도록 설계했습니다. 필터는 신규 재난을 놓치지 않도록 화이트리스트가 아닌 denylist로 택해, 안전 시스템에서 미탐을 오탐보다 무겁게 다뤘습니다."

### 3-19. 클라이언트 사이드 레이트 리미팅 — 분당 한도를 넘지 않게 스스로 조절

💡 **개념.**
호출 한도(quota)에는 두 종류가 있다. **일일 한도**는 "하루 총 몇 번"이라 폴링 주기로 통제한다(3-15). **분당(초당) 한도**는 "짧은 창 안에 몇 번"이라 폴링 주기로는 못 막는다 — 한 사이클 안에서 여러 번 호출하면 그 순간의 **호출 속도(rate)**가 문제이기 때문이다. 이때 필요한 게 **클라이언트 사이드 레이트 리미터**: 내가 만드는 요청 속도에 스스로 상한을 걸어, 서버가 나를 차단하기 전에 내가 먼저 속도를 낮춘다. 가장 단순한 구현은 **최소 간격 게이트** — "직전 호출로부터 최소 T초가 지나야 다음 호출을 허용"하고, 안 지났으면 그만큼 `sleep`한다. `분당 최대 N회`면 `T = 60/N`. 병렬을 순차로 바꾸는 것만으로는 부족하다는 게 핵심: 순차라도 각 호출이 빠르면(네트워크가 빠르면) 속도가 한도를 넘을 수 있다. 속도 자체에 바닥을 깔아야 한다.

🔧 **이 프로젝트에서.**
홍수통제소는 분당 1,000건을 넘기면(초과 3회) 키가 차단된다. 지금은 관측소 2개(사이클당 3콜)라 여유롭지만, 로드맵의 "관측소 동적 선정"(구독 지역에 맞춰 N개 순회)을 켜면 N이 커진다 — 전국 1,417개 × 콜당 50ms면 분당 1,200콜로 한도를 넘긴다. 그래서 `hrfco_flood.py`에 `_RateLimiter`를 넣어 **모든 outbound 호출(관측소 목록 + 관측소별 수위) 직전에 `wait()`로 게이트**했다. 상한은 한도의 60%인 분당 600(콜당 최소 0.1초)으로, N이 아무리 커져도 절대 한도를 못 넘는다. 설정(`HRFCO_MAX_REQUESTS_PER_MINUTE`)으로 조정 가능. 이건 스케줄러 중복 가드·LLM 쿨다운·이벤트 dedupe와 같은 **"상태(직전 호출 시각)를 기억해 낭비/위험 호출을 막는다"** 모티프의 또 다른 변주다. 테스트는 리미터에 가짜 시계(`monotonic`)와 `sleep`을 주입해 **실제 대기 없이** "600회 호출 시 총 59.9초로 눌린다", "간격이 충분하면 대기 안 한다"를 결정론적으로 검증했다.

🎤 **면접 한마디.**
"일일 한도는 폴링 주기로, 분당 한도는 클라이언트 사이드 레이트 리미터로 통제했습니다. 관측소를 여러 개 순회하면 순차 호출이라도 속도가 한도를 넘을 수 있어, 호출 직전 최소 간격 게이트로 속도 자체에 상한을 걸었습니다. 리미터에 시계와 sleep을 주입해 실제 대기 없이 테스트했습니다."

### 3-20. 생성과 발송의 분리 + FCM v1(서비스계정 OAuth2) — 푸시 파이프라인

💡 **개념.**
알림 시스템에서 "알림을 **만드는** 일"과 "알림을 **보내는** 일"은 분리하는 게 정석이다. 한 트랜잭션에서 둘을 같이 하면(인라인 발송), 외부 발송이 실패할 때 생성 로직까지 얽히고, 재시도·중복발송 제어가 어려워진다. 대신 알림을 DB에 "미발송" 상태로 쌓아두고(`sent_at=NULL`), **별도 dispatch 단계**가 미발송분만 모아 보낸 뒤 성공한 것에 `sent_at`을 찍는다. 이러면 `sent_at`이 곧 **멱등 가드**가 되어: 성공분은 다시 안 보내고, 실패분(네트워크·5xx)은 다음 사이클에 자동 재시도되며, 생성과 전송이 서로를 붙들지 않는다(관심사 분리). 이건 이 프로젝트에 반복되는 "상태를 기억해 낭비/중복 호출을 막는다" 모티프(스케줄러 가드·LLM 쿨다운·이벤트 dedupe·레이트 리미터)의 또 다른 얼굴이다.

또 하나의 개념: **인증 방식은 시간이 지나면 폐기(deprecate)된다.** 예전 FCM은 "서버 키" 하나를 헤더에 넣으면 끝이었지만, 구글이 2024.6에 그 방식을 닫았다. 지금은 **서비스계정(JSON) → 단명(short-lived) OAuth2 액세스 토큰 → Bearer 헤더**의 v1 API만 동작한다. 서버키(영구 비밀 하나)보다 서비스계정+단명 토큰이 더 안전하다 — 토큰이 새도 곧 만료되고, 권한을 스코프로 좁힐 수 있다. 라이브러리(`google-auth`)가 JSON으로 토큰을 발급·자동 갱신해주므로 우리가 만료를 신경 쓸 필요는 없다.

🔧 **이 프로젝트에서.**
- **발송 분리(dispatch).** `app/services/dispatch.py`가 `sent_at IS NULL` 알림을 모아, 각 알림의 (구독→사용자→기기토큰)으로 FCM 발송하고 성공 시 `sent_at`을 찍는다. ingest 사이클 끝에서 호출되므로(스케줄러·수동 `/events/ingest` 공통), 이번에 만든 알림뿐 아니라 지난번에 못 보낸 것까지 매 사이클 flush된다. 죽은 토큰(FCM 404 UNREGISTERED)은 그 자리에서 삭제해 다음부터 헛발송을 막는다.
- **FCM v1 클라이언트.** `app/services/push.py`. 프로젝트ID·서비스계정 파일이 설정돼 있으면 실발송, 없으면 **no-op(mock)** — ingestion 클라이언트가 키 없으면 `_fetch_mock`을 쓰는 것과 똑같은 graceful degradation. 덕분에 서비스계정 JSON이 아직 없어도 등록→생성→발송 파이프라인 전체를 개발·테스트할 수 있고, `secrets/`에 JSON만 넣으면 실발송으로 자동 전환된다. `google-auth`/`requests`는 실발송 경로에서만 **지연 import**라, 미설정 환경에선 그 패키지가 없어도 앱이 뜬다.
- **레거시 정리.** 폐기된 `fcm_server_key` 설정을 제거하고 `fcm_project_id`+`fcm_credentials_file`(env는 관례명 `GOOGLE_APPLICATION_CREDENTIALS`)로 교체. 로그 마스킹 목록에서도 뺐다.
- **테스트(외부 의존 0).** mock 모드 분기, 실발송 성공(`_access_token`·`httpx.post` monkeypatch), 죽은 토큰(404)·transient(5xx) 분기, 토큰 등록 멱등, dispatch의 발송/미대상/멱등/죽은토큰정리, end-to-end(토큰 등록 후 한 사이클에서 생성→발송)까지 11개. conftest가 FCM 설정도 비워 테스트가 실제 서비스계정 없이 mock으로 돈다.

🎤 **면접 한마디.**
"알림 생성과 발송을 분리해, 알림을 sent_at=NULL로 쌓고 별도 dispatch가 미발송분만 보낸 뒤 sent_at을 찍게 했습니다. sent_at이 멱등 가드라 중복발송을 막고 실패는 자동 재시도됩니다. FCM은 폐기된 서버키 대신 서비스계정 OAuth2 v1으로 붙였고, 자격증명이 없으면 no-op로 degrade해 파이프라인 전체를 자격증명 없이도 테스트할 수 있게 했습니다."

### 3-21. 웹 PWA와 서비스워커 — 브라우저가 푸시를 받는 원리

💡 **개념.**
**PWA(Progressive Web App)**는 "웹페이지인데 앱처럼 동작하는" 것 — 홈 화면 설치(`manifest.json`), 오프라인, 그리고 **푸시 알림**이 핵심 능력이다. 푸시의 열쇠는 **서비스워커(Service Worker)**: 페이지와 별개로 브라우저가 백그라운드에서 돌려주는 JS 스크립트라, **탭이 닫혀 있어도** 푸시 메시지를 받아 알림을 띄울 수 있다. 웹푸시 수신 절차는 4단계다: ① 사용자에게 알림 권한 요청 → ② 서비스워커 등록 → ③ 푸시 서비스(FCM)에서 **이 브라우저를 가리키는 토큰** 발급 → ④ 그 토큰을 서버에 등록. 이후 서버가 그 토큰으로 FCM에 보내면, FCM이 브라우저를 깨워 서비스워커가 알림을 표시한다. **VAPID 키**는 "이 푸시를 보낼 자격이 있는 서버"임을 증명하는 공개키/비밀키 쌍 — 토큰 발급 때 공개키를 제시해, 아무 서버나 내 브라우저에 푸시를 못 쏘게 막는다. 참고로 Firebase **웹 클라이언트 설정(apiKey 등)은 시크릿이 아니다** — 모든 방문자의 브라우저에 배포되는 공개 식별자로, 보안은 서버 쪽 규칙이 담당한다.

🔧 **이 프로젝트에서.**
`app/static/`에 순수 HTML+JS로 구독 화면을 만들고 FastAPI가 직접 서빙하게 했다(`GET /app`) — Node/React 없이 uvicorn 하나로 백엔드+프론트가 다 돈다(MVP 최소 구성). 화면 흐름은 이메일(임시 인증) → 보호 대상 등록 → 지역 구독 → "알림 켜기"(권한→SW등록→FCM 토큰 발급→`POST /device-tokens`) → 알림 내역. 재미있는 설계 지점 두 가지: (1) **서비스워커를 동적 생성** — SW는 별도 파일이라 페이지의 설정을 못 받는데, 설정을 하드코딩하면 설정이 코드에 흩어진다. 그래서 `GET /firebase-messaging-sw.js` 라우트가 `.env`의 Firebase 웹 설정을 박아 넣은 JS를 만들어 준다. SW의 제어 범위(scope)는 "서빙된 경로 이하"라 루트 경로에서 서빙해야 `/app`을 제어할 수 있다는 것도 이 방식이면 자연스럽다. (2) **graceful degradation** — `GET /firebase-config`가 `enabled=false`면 프론트는 알림 버튼만 비활성화하고 구독 관리는 그대로 동작한다. ingestion mock, 발송 mock과 같은 결.

🎤 **면접 한마디.**
"웹푸시는 권한→서비스워커→토큰 발급→서버 등록 4단계로 붙였습니다. 서비스워커는 Firebase 설정이 필요한데 정적 파일에 하드코딩하는 대신 서버가 설정을 주입해 동적 서빙했고, 설정이 없으면 알림 기능만 꺼지고 나머지는 동작하게 degrade했습니다. 빌드 도구 없이 FastAPI 정적 서빙으로 백엔드+프론트를 프로세스 하나에 담아 MVP 비용을 최소화했습니다."

### 3-22. 이름 기반 지역 매칭 + 웹푸시 실전 함정 두 가지

💡 **개념.**
**(1) 서로 다른 체계의 지역명 매칭.** 사용자는 행정구역명(경주시, 부산광역시)을 알지만, 기상청 특보는 **예보구역명**(경주남부, 부산 전체)으로 나온다. 문자열이 같아야 하는 ID 동일성 매칭은 이 간극에서 조용히 실패한다. 해결은 매칭 규칙을 계층화하는 것: ① 시도명 표준화(접두어 사전 — 부산광역시↔부산, 전북특별자치도↔전북자치도) ② 광역 단위('전체') 포함 판정 ③ 시군구 접두어 비교('경주' ⊂ '경주남부'). 완벽하진 않지만(제주도산지 같은 비행정 구역은 못 잡음) 표준 코드 매핑 전까지의 실용적 중간 해다.

**(2) 웹푸시의 실전 함정.** 첫째, **user activation**: 브라우저는 권한 팝업을 "사용자 제스처 직후"에만 허용한다. 버튼 핸들러 안이라도 `await fetch(...)`를 먼저 하면 활성화가 소진돼 모바일 크롬이 **팝업 없이 조용히 거부**한다 — 권한 요청은 클릭 직후 첫 번째 await 여야 한다. 둘째, **포그라운드/백그라운드 분기**: 탭이 닫혀 있으면 서비스워커가 알림을 자동 표시하지만, **탭이 화면에 열려 있으면 메시지가 페이지로 직접 오고 onMessage 핸들러가 없으면 조용히 버려진다**. 서버가 FCM 200을 받아도 사용자 눈에 아무것도 안 보일 수 있다는 뜻 — "발송 성공 ≠ 표시 성공".

🔧 **이 프로젝트에서.**
매칭은 `crud.regions_match`(시도 표준화 + 전체 + 접두어)로 구현하고 `_evaluate_and_notify`·`backfill_subscription`이 region_id 동일성 대신 이걸 쓰게 바꿨다. 덕분에 프론트 드롭다운은 익숙한 표준 행정구역 17개 시도(districts.js)를 하드코딩해도 되고, 실기기에서 "경주시" 구독이 경주남부·서부·동부·중북부 특보 4건과 매칭됨을 실증했다. 웹푸시 함정은 둘 다 실기기에서 실제로 겪었다: 모바일 크롬에서 팝업이 안 떠서(요청 전에 /firebase-config fetch가 있었음) 권한 요청을 클릭 직후로 옮겼고, FCM 200인데 폰에 아무것도 안 떠서(탭이 열려 있었음) 포그라운드 onMessage 핸들러 + `registration.showNotification`을 추가했다. 탭을 닫고 재발송하자 시스템 알림이 도착 — 백그라운드/포그라운드 양쪽 검증 완료.

🎤 **면접 한마디.**
"사용자의 행정구역명과 기상청 예보구역명이 달라 ID 매칭이 조용히 실패하는 문제를, 시도 표준화·광역 포함·접두어 비교의 3단 규칙으로 풀고 실기기로 실증했습니다. 웹푸시에선 user activation 소진과 포그라운드 무표시라는 두 함정을 실기기 디버깅으로 잡았는데, '서버의 발송 성공이 곧 사용자 눈의 표시 성공은 아니다'가 교훈이었습니다."

### 3-23. JWT + OAuth 소셜 로그인 — 비밀번호 없는 인증

💡 **개념.**
**(1) JWT(JSON Web Token)** 는 서버가 비밀키로 **서명해서 발급하는 디지털 신분증**이다. 내용(누구인지, 언제 만료되는지)은 누구나 읽을 수 있지만, 비밀키 없이는 내용을 바꿔 유효한 서명을 만들 수 없다 — 그래서 클라이언트가 주장하는 값(`user_email` 파라미터)과 달리 위조가 안 된다. 서버가 "로그인한 사람 명단"을 들고 있을 필요가 없는 **무상태(stateless)** 인증이라 확장에 유리하고, 대신 만료 전 강제 무효화가 안 되는 게 트레이드오프다. 만료시간의 진짜 의미는 "사용자가 얼마나 자주 오나"가 아니라 **"도둑맞은 토큰이 유효한 시간 창"**이다.
**(2) OAuth 인가 코드 흐름(서버사이드)**: 사용자를 프로바이더(구글/카카오) 동의 화면으로 보내고, 콜백으로 받은 일회용 `code` 를 **서버가 직접** 프로바이더 토큰 엔드포인트에서 교환한다. 비밀번호를 우리가 절대 만지지 않고, `client_secret` 도 서버에만 있다. `state` 파라미터(랜덤 값을 쿠키에 넣고 콜백에서 대조)로 CSRF 를 막는다. 프로바이더 토큰은 "그 프로바이더에게" 나를 증명하는 것이므로, 로그인 순간에만 쓰고 이후 API 는 **우리가 서명한 JWT** 로 인증한다 — 프로바이더 장애·정책과 우리 API 인증이 분리된다.
**(3) 소셜 로그인의 함정들**: 사용자 식별은 이메일이 아니라 **프로바이더 회원번호**(구글 `sub`, 카카오 `id`)로 한다 — 카카오 이메일은 비즈 앱 전환이 필요하고, "이메일 같으면 자동 계정 통합"은 탈취 벡터다. 구글은 **인앱 브라우저(카톡 등 웹뷰)에서 OAuth 를 차단**(`disallowed_useragent`)하므로 카카오 로그인과 병행하는 게 상호 보완이 된다. 발급된 토큰을 프론트로 넘길 땐 URL **fragment**(`#token=...`)를 쓴다 — 쿼리스트링과 달리 서버 로그·프록시에 남지 않는다.

🔧 **이 프로젝트에서.**
`user_email` 임시 방식(아무나 남의 이메일로 조회 가능)을 구글+카카오 소셜 로그인 + 30일 단일 JWT 로 교체했다. users 는 `(auth_provider, provider_user_id)` 쌍 유니크로 개편(이메일·비밀번호 미수집 — 해시·유출 걱정 자체가 없다), `/auth/{google,kakao}/login·callback` 이 code 교환 후 `issue_token()` 으로 HS256 JWT 를 발급, FastAPI 의존성 `get_current_user` 한 줄이 라우트 4개의 인증을 대체했다. 만료 30일 근거: 이 서비스는 구독 설정 말고 방문할 일이 없고 **푸시 발송은 JWT 와 무관**하므로 만료 비용이 "가끔 재로그인"뿐 — access+refresh 이중 토큰은 그 위에 얹는 확장으로 남겼다. 남용 방어는 인증이 아니라 **쿼터**(person_limit 3, 초과 시 409)가 맡는다 — 인증을 아무리 세게 해도 정당한 1계정이 구독 1,000개 만드는 건 못 막기 때문. PyJWT 함정 하나: `verify_signature=False` 면 aud/iss 검증도 같이 꺼지므로 구글 id_token 의 aud(우리 client_id)·iss 는 수동으로 검사한다.

🎤 **면접 한마디.**
"클라이언트가 주장하는 식별자를 서버가 서명한 JWT 로 교체하고, 소셜 로그인은 이메일 대신 프로바이더 회원번호로 식별해 계정 자동 통합의 탈취 벡터를 피했습니다. 만료시간은 방문 주기가 아니라 '도난 토큰의 유효 시간 창'이라는 기준으로 30일 단일 토큰을 선택했고, 남용 방어는 인증이 아니라 계정당 쿼터가 맡는다고 역할을 분리했습니다."

### 3-24. 인앱 브라우저(웹뷰) — 감지와 탈출 유도

💡 **개념.**
카카오톡·인스타그램 등에서 링크를 누르면 크롬/사파리가 아니라 **그 앱 안에 내장된 브라우저(웹뷰)** 가 열린다. 화면만 보면 브라우저지만 실제로는 앱의 일부라서 제약이 많다: 구글은 **정책상 웹뷰에서 OAuth 로그인을 거부**하고(`disallowed_useragent` — 웹뷰는 앱 개발자가 화면·자바스크립트를 들여다볼 수 있어 비밀번호 입력이 안전하지 않다), 웹푸시·서비스워커도 앱마다 되거나 안 된다. 즉 "브라우저에서는 되는데 카톡에서 누르면 안 되는" 상태가 정상 동작이다.
**감지 방법.** "지금 인앱인가?"를 알려주는 표준 API 는 없다. 앱들이 **User-Agent 문자열에 자기 이름을 덧붙이는** 관행(`... KAKAOTALK 25.2.1`, `Instagram 340...`, `[FBAN/FBIOS...]`)을 이용해 패턴 매칭하는 게 현실적인 방법이다. 신뢰성이 낮은 신호이므로 **오탐(정상 브라우저에 경고를 띄움)이 미탐보다 나쁘다**는 기준으로 규칙을 좁게 잡는다.
**탈출 방법.** 앱마다 제각각이다. 카카오톡은 커스텀 스킴(`kakaotalk://web/openExternal?url=...`), 라인은 쿼리 파라미터(`openExternalBrowser=1`)를 제공하고, 인스타·페이스북은 표준 방법이 없어 "주소 복사 후 붙여넣기" 안내가 최선이다.

🔧 **이 프로젝트에서.**
주 유입 경로가 "카톡으로 부모님께 링크 보내기"라 이 문제는 이론이 아니라 **첫 사용자가 100% 만나는 벽**이다. `app/static/inapp.js` 에 감지 규칙표와 탈출 URL 생성을 모으고, `/login`·`/app` 두 화면이 같은 배너 마크업을 공유하게 했다(탈출 가능하면 "Chrome·Safari 로 열기", 불가하면 "주소 복사하기"). 규칙표는 UA 6종을 잡고, 정상 브라우저 6종(안드로이드 크롬·iOS 사파리·CriOS·삼성인터넷·**웨일**·데스크톱 사파리)은 절대 안 잡히도록 회귀 테스트를 뒀다 — 웨일은 UA 에 `NAVER` 가 들어가지만 인앱이 아니라 오탐 위험이 큰 케이스다. 테스트는 모듈이 **불러와도 아무 일도 하지 않게**(DOM 접근은 함수 안에서만) 만들어 node 로 규칙표를 그대로 실행해 검증한다(node 없으면 skip — 파이썬 전용 환경을 깨지 않게). 함정 하나: 브라우저는 확장자와 무관하게 ES 모듈로 읽지만 node 는 `package.json` 없는 `.js` 를 CommonJS 로 취급해 `import` 가 실패하므로, 테스트는 소스를 이어붙여 실행한다.

🎤 **면접 한마디.**
"공유 링크가 카톡 인앱 브라우저에서 열리면 구글 OAuth 가 정책상 차단돼 '고장난 서비스'로 보이는 문제를, UA 패턴 감지 + 앱별 탈출 스킴 안내로 풀었습니다. 신뢰도가 낮은 신호라 오탐이 미탐보다 비싸다고 보고 규칙을 좁게 잡았고, 정상 브라우저(특히 UA 에 NAVER 가 들어가는 웨일)를 오탐하지 않는지 회귀 테스트로 고정했습니다."

### 3-25. 시계를 밖으로 — 인프로세스 루프에서 외부 cron으로 (그리고 콜드 스타트)

💡 **개념.**
"10분마다 뭔가를 한다"를 구현할 자리는 두 곳이다. **앱 프로세스 안**(asyncio 무한 루프, APScheduler)이거나, **앱 밖의 관리형 cron**(Cloud Scheduler, EventBridge, 크론탭)이 인증된 HTTP 요청을 보내는 방식이다. 차이는 한 문장으로 요약된다 — **"시간을 아는 주체가 누구인가."**

프로세스 안에 두면 배포가 단순하다. 프로세스 하나만 띄우면 웹도 배치도 같이 돈다. 대가는 **시계의 수명이 프로세스의 수명과 같아진다**는 것이다. 프로세스가 죽으면 시계도 죽고, 프로세스를 2개로 늘리면 시계도 2개가 된다. 후자가 특히 무섭다 — 확장했더니 외부 API 호출량이 2배가 되는 구조라면, **확장이 곧 한도 초과**다.

밖으로 빼면 앱은 "요청이 오면 일하는 무상태 서비스" 하나로 단일화된다. 스케줄 변경·실패 재시도·실행 이력이 코드가 아니라 **플랫폼 설정**이 된다. 대가는 두 가지다. 그 엔드포인트에 **인증이 필수**가 되고(누구나 부를 수 있으면 스케줄러가 무슨 의미인가), 관리할 인프라가 하나 늘어난다.

그리고 **서버리스(scale-to-zero)에서는 이게 선택이 아니라 필수**다. 요청이 없을 때 프로세스가 존재하지 않으므로, 인프로세스 무한 루프는 돌 프로세스 자체가 없다.

**콜드 스타트도 같은 뿌리에서 나온다.** 요청이 없으면 컨테이너가 없으니, 오랜만에 온 요청은 "컨테이너 만들기 → 파이썬 시작 → import → 첫 DB 연결"을 기다린다(체감 1~3초). 여기서 흔한 오해가 두 개 있다. ① **"유휴 몇 분 뒤 꺼진다"는 보장된 숫자가 아니다** — 구글은 회수 타이밍을 공개하지 않으므로 "15분"류의 숫자는 관측치일 뿐이다. ② **cron 이 keep-warm 역할을 겸한다** — 10분마다 요청이 오면 회수 타이머가 계속 리셋되므로 대체로 따뜻하게 유지되고, 콜드 스타트 비용은 사용자가 아니라 cron 이 낸다(배치가 3초 늦는 건 아무 문제가 아니다). 단 이건 **확률이지 보장이 아니다** — 배포 직후, 크래시 직후, 회수가 cron 주기보다 빨랐을 때는 사용자가 맞는다.

🔧 **이 프로젝트에서.**
**7월 20일의 결정은 인프로세스 루프였다.** APScheduler 를 쓰지 않고 asyncio 만으로 최소 구성했다. 단일 프로세스 MVP 에서는 그게 맞았고, 그때 퇴로를 주석과 노트에 남겼다 — "다중 인스턴스면 `SCHEDULER_ENABLED=0` 으로 끄고 외부 스케줄러로 전환". **7월 27일 배포를 준비하면서 그 퇴로가 실제로 필요해졌다.** 클라우드에 올리는 순간 이 코드가 깔고 있던 두 가정이 깨지기 때문이다.

**가정 ①: 인스턴스는 하나다.** 중복 실행 가드의 상태가 모듈 전역 변수(`_last_cycle_at`)였다. 인스턴스 A 가 "방금 수집했다"고 기억해도 B 는 모르므로, 인스턴스가 늘면 가드가 조용히 무력해진다. 이게 왜 치명적인지는 3-15(호출량 예산)와 붙여 보면 분명해진다 — 하루 144사이클로 계산한 예산이 **인스턴스 수만큼 곱해지고**, 가장 빡빡한 긴급재난문자(1,000건/일)는 14.4% → 43%(3인스턴스)로 뛴다. 그래서 가드 상태를 `ingest_runs` 테이블로 옮겼다. 겸해서 "언제 몇 건 들어왔고 어떤 소스가 실패했나"가 행으로 남아, 로그 grep 없이 조회할 수 있게 됐다(`finished_at` 이 NULL 인 행 = 도중에 죽은 사이클). 남은 한계는 정직하게 적어둔다: read-then-write 경합(두 인스턴스가 같은 순간 조회)은 막지 않는다 — 외부 cron 이 단일 호출자라 현실 위험이 낮고, 필요해지면 DB 락으로 좁힌다.

**가정 ②: 호출하는 사람은 나뿐이다.** `POST /events/ingest` 가 무인증이었다. 흥미로운 건 7월 20일 일지에도 이 엔드포인트를 "무방비"라고 적어놨다는 점인데, **당시 위협 모델은 "내가 실수로 연타하는 것"이었고 해법은 시간 가드였다.** 공개 배포에서의 위협은 "주소를 아는 타인이 고의로 반복 호출해 남의 공공 API 쿼터와 LLM 비용을 태우는 것"이고, 여기엔 **시간 가드가 답이 아니다 — 가드는 낭비를 줄이지만 인증이 아니다.** 같은 코드, 같은 "무방비"라는 표현인데 배포라는 조건 변화가 필요한 대응을 바꿨다.

인증 방식으로 **앱 레벨 공유 시크릿**(`X-Ingest-Token` 헤더)을 골랐다. Cloud Run 의 IAM 인증이 더 정석처럼 보이지만 **서비스 단위 all-or-nothing** 이라, 같은 서비스가 공개 페이지(`/login`·`/app`)도 서빙하는 구조에서는 쓸 수 없다(웹과 수집 잡을 별도 서비스로 쪼개면 가능하지만 인프라가 늘어 보류). 그리고 토큰이 설정되지 않았으면 **열어두지 않고 503 으로 막는다(fail-closed)** — "설정을 잊으면 열려 있는" 보호는 없는 것보다 위험하다. 로컬 자동 수집은 스케줄러가 서비스 함수를 직접 호출하므로 영향이 없고, 막히는 건 HTTP 수동 트리거뿐이다.

**작은 함정 두 개를 실제로 밟았다.** ① `secrets.compare_digest` 는 **비ASCII 문자열에 TypeError** 를 던진다. HTTP 헤더는 latin-1 로 디코드되므로 그런 값이 실제로 도착할 수 있고, 그러면 401 이어야 할 요청이 500 이 된다. bytes 로 인코딩해 비교하도록 고치고 회귀 테스트를 넣었다. ② **`--proxy-headers` 만으로는 부족하다.** uvicorn 은 신뢰 목록(기본 `127.0.0.1`)에서 온 `X-Forwarded-*` 만 반영하는데, 컨테이너 밖 프록시의 IP 는 127.0.0.1 이 아니다. 어제 cloudflared 터널이 통했던 건 터널이 localhost 에서 붙어서였고, Cloud Run 은 프록시 IP 가 달라 **그대로 배포하면 OAuth 리다이렉트가 다시 http 로 생성돼 로그인이 깨질 자리**였다. `--forwarded-allow-ips=*` 를 추가하고 컨테이너에서 `X-Forwarded-Proto: https` → `redirect_uri=https://...` 로 검증했다.

**콜드 스타트는 "무엇이 느려지는가"를 나눠서 판단했다.** 결론부터 말하면 **푸시 알림은 콜드 스타트와 무관하다** — 알림은 FCM(구글 서버)이 폰으로 보내고, 우리 서버는 발송을 요청하는 순간에만 필요한데 그 순간은 cron 이 방금 깨운 시점이라 이미 따뜻하다. 즉 특보가 왔는데 알림이 늦는 일은 없다. 느려지는 건 **사람이 브라우저로 페이지를 여는 순간**뿐이고, 이 서비스는 구독 설정할 때 한 번 오고 몇 주 안 온다. 그래서 대응을 "로딩 표시"로 정했다(`min-instances=1` 은 콜드 스타트를 없애주는 유일한 보장이지만 유휴 과금이 붙어 "거의 무료"를 포기하는 결정이 된다). 여기서도 한계를 분명히 해둔다 — **로딩 표시가 덮는 건 "페이지가 뜬 뒤 API 를 기다리는 구간"뿐이다.** 콜드 스타트로 HTML 자체를 기다리는 구간은 우리 JS 가 아직 실행되기 전이라 손댈 수 없고, 그 구간은 브라우저 탭의 로딩 표시가 담당한다. DB 도 잠든다는 점도 겹친다(Neon 무료 티어는 유휴 시 대기 → 깨우는 데 추가 지연). 최종 판단은 배포 후 `curl -w "%{time_total}"` 로 콜드/웜을 **재서** 하기로 했다.

🎤 **면접 한마디.**
"주기 실행을 프로세스 안에 둔 초기 선택은 단일 프로세스 MVP 에 맞는 결정이었고, 그때 전환 퇴로를 코드 주석과 문서에 남겨뒀습니다. 배포를 준비하면서 그 코드가 깔고 있던 가정 두 개 — 인스턴스는 하나다, 호출자는 나뿐이다 — 를 명시적으로 검사했고, 각각을 가드 상태의 DB 이전과 엔드포인트 토큰 인증으로 해소했습니다. 특히 같은 엔드포인트를 두고 '실수 연타'와 '타인의 고의'는 다른 위협이고 시간 가드는 후자의 답이 아니라는 점, 그리고 콜드 스타트가 푸시 발송이 아니라 사람의 페이지 방문에만 영향한다는 점을 나눠서 판단해 비용 0원 구성을 유지했습니다."

### 3-26. 조용한 실패 — "돌고 있다"와 "제대로 되고 있다"는 다른 질문이다

💡 **개념.**
서비스가 죽으면 알기 쉽다. 헬스체크가 빨개지고, 5xx 가 뜨고, 사람이 전화한다. 진짜 무서운 건 **죽지 않은 채로 하는 일만 안 하는 상태**다. 프로세스는 살아 있고 응답도 200 이고 로그도 에러가 없는데, 정작 사용자에게 도착해야 하는 결과만 도착하지 않는다. 이걸 조용한 실패(silent failure)라고 한다.

왜 유독 잘 안 들키냐면, 우리가 보통 감시하는 건 **가동(liveness)** 이고 조용한 실패는 **성과(outcome)** 의 문제이기 때문이다. `/health` 200 은 "서버가 요청을 받는다"만 말해준다. "오늘 보내야 할 알림 8건이 아직 안 나갔다"는 전혀 다른 질문이고, 그건 도메인을 아는 사람이 일부러 세어봐야 나오는 숫자다.

조용한 실패가 태어나는 전형적인 구조가 두 가지 있다.

- **결과를 아무도 안 보는 구조.** 함수가 결과를 리턴하는데, 그 리턴값을 받는 쪽이 사람이 아니라 기계이고, 기계는 그걸 버린다. 로컬에서 눈으로 보던 값이 배포 후엔 아무 데도 안 남는다.
- **복구 경로가 없는 구조.** "언젠가 반드시 일어나는 일"(토큰 만료, 캐시 무효화, 세션 종료)에 대해 정리(cleanup)는 구현했는데 **재생성(recovery)** 은 사용자의 특정 행동에만 걸어둔 경우. 정리는 자동인데 복구는 수동이면, 시간이 지날수록 시스템은 한 방향으로만 흘러가 결국 아무것도 없는 상태에 도달한다.

대응은 화려한 모니터링 도구가 아니라 두 가지 습관으로 시작한다. ① **결과를 로그로 남기고, 사람이 알아야 하는 상황만 WARNING 으로 올린다** — 정상일 때 조용해야 경고가 의미를 가진다(모든 사이클이 경고를 뿜으면 아무도 안 읽는다). ② **정리 코드를 쓸 때 복구 코드를 같이 쓴다** — "무엇이 이걸 다시 만들어주나?"에 답이 없으면 그 정리는 편도 티켓이다.

🔧 **이 프로젝트에서.**
7월 30일, 배포 3일 뒤에 프로덕션을 열어봤다. 겉보기 지표는 전부 좋았다 — 수집 401회 전부 200, 5xx 0건, 웜 응답 0.3초, 시크릿 마스킹 정상. 그런데 DB 를 세어보니 **등록된 기기 토큰 0개, 미발송 알림 8건, 마지막 발송은 이틀 전**이었다. 폭염특보·화재위험경보가 대전에 떴고 문구까지 생성됐는데 폰으로는 한 건도 가지 않았다.

두 구조가 정확히 다 있었다. **하나:** 토큰이 죽으면(FCM 이 404 UNREGISTERED 를 주면) dispatch 가 죽은 토큰을 지운다 — 이건 옳다. 그런데 토큰을 **다시 만드는 경로가 "구독 폼 제출" 하나뿐**이었다. 웹푸시 토큰은 원래 죽는다(사이트 데이터 삭제, 브라우저의 구독 갱신). 즉 "언젠가 반드시 일어나는 일"에 대해 정리는 자동, 복구는 수동이었고, 그래서 한 번 죽은 뒤엔 영구히 안 갔다. 더 나쁜 건 클라이언트가 발급받은 토큰을 localStorage 에 캐시하고 **캐시가 있으면 FCM 에 다시 묻지 않았다는 점** — 사용자가 재등록을 눌러도 죽은 값이 다시 등록되고 다음 발송에서 또 지워진다. 스스로 못 낫는 상태였다.

**둘:** 이걸 이틀 동안 아무도 몰랐던 이유는 로그가 **한 줄도** 없었기 때문이다. `ingest.py` 와 dispatch 에 logger 가 아예 없었다. 로컬에서는 스케줄러가 서비스 함수를 직접 호출하고 결과 dict 를 콘솔에서 눈으로 봤으니 필요가 없었는데, Cloud Scheduler 로 옮기면서 그 dict 가 **HTTP 응답으로 나가고 Scheduler 가 버린다.** 3-25 에서 "시계를 밖으로 뺐다"고 썼는데, 그때 같이 빠져나간 게 하나 더 있었다 — **결과를 보던 사람.**

고친 것도 그 둘이다. 사이클 끝에 한 줄 요약(INFO), 사람이 알아야 하는 상황만 WARNING(죽은 토큰 정리 / 보낼 기기 없음 / 발송 실패), 그리고 **정상일 때는 WARNING 이 없어야 한다는 것까지 테스트로 고정**했다. 복구 쪽은 `/app` 을 열 때마다 현재 토큰을 FCM 에 물어 서버와 맞추도록 했다(서버 등록이 멱등이라 무조건 POST 해도 안전). 캐시는 "이 기기에서 알림을 켠 적 있나" 힌트로만 남겼다. 덤으로 화면에 "✅ 이 기기로 알림을 받는 중이에요" 배지를 붙였다 — 조용한 실패를 사용자도 볼 수 있게.

🎤 **면접 한마디.**
"배포 3일 뒤 점검에서 헬스체크·에러율·응답속도는 전부 정상인데 알림만 이틀째 안 나가고 있는 걸 발견했습니다. 원인은 두 겹이었는데, 죽은 푸시 토큰을 정리하는 코드는 있었지만 재생성 경로가 특정 사용자 행동에만 걸려 있어서 한 번 끊기면 영구히 복구되지 않는 구조였고, 그걸 이틀간 몰랐던 이유는 주기 실행을 외부 스케줄러로 옮기면서 결과를 사람이 보는 경로가 사라졌기 때문이었습니다. 결과 요약 로그와 경고 기준을 넣고, 정리 코드마다 '무엇이 이걸 다시 만들어주나'를 짝지어 자동 복구 경로를 만들었습니다. 그 뒤로는 '살아 있나' 대신 '오늘 몇 건 보냈나'를 보고 있습니다."

### 2026-07-17 — 로컬 실행 환경 구축 + 실제 API 연동 (FDE의 하루)

**로컬 환경 구축에서 배운 것들.** Docker Desktop 설치 → Postgres 컨테이너 기동 → `alembic upgrade head`로 실제 Postgres에 12개 테이블 생성 성공. 과정에서 겪은 실전 문제들:
- 맥 기본 python3가 3.9라 프로젝트 요구(3.10+ 문법)와 안 맞음 → Homebrew로 3.12 설치 후 venv 재생성. psycopg2-binary가 3.9에선 미리빌드 휠이 안 잡혀 pg_config 에러가 났던 것도 같은 뿌리.
- 명령어를 주석(`# ...`)까지 복붙했더니 zsh가 주석으로 안 치고 인자로 받아 `새로`, `맥용으로` 같은 이름의 venv가 생기는 사고. 교훈: 셸에 붙여넣는 명령은 주석 없이.
- 가상환경은 터미널 열 때마다 `source .venv/bin/activate` 필요.

**실제 API 대조 — 추정 코드는 전부 틀렸다.** `_fetch_live()`는 문서 없이 data.go.kr 공통 컨벤션으로 추정해 짠 코드였는데, 첫 실 호출에서 500. `debug_fetch.py`(응답을 파일로 덤프하는 1회성 도구)를 만들어 실 응답을 뜨고, 그걸 근거로 3개 클라이언트를 전부 고쳤다:
- **기상특보**: `items`가 리스트가 아니라 `{"item": [...]}`(data.go.kr 공통 함정). 특보 종류·등급·조치가 별도 필드가 아니라 `title` 문자열("... / 폭염주의보 발표 (*)")에 박혀 있어 정규식 파싱. `stnId`는 시군구가 아니라 발표 관서 코드 → 지역 매칭은 통보문 상세(getWthrWrnMsg, `t6` 필드에 지역 텍스트 확인됨) 연동이 필요 (TODO).
- **지진**: 필수 파라미터 `fromTmFc`/`toTmFc` 누락으로 resultCode=11. 넣었더니 이번엔 "최대 조회 기간 3일" 제한(resultCode=99). 에러 메시지가 다음 스펙을 알려주는 셈 — 실 호출 없이는 알 수 없는 제약들. 발생시각은 `tmEqk`(yyyyMMddHHmmss).
- **홍수통제소**: 코드의 URL이 웹페이지 placeholder였음. 실제 API는 `api.hrfco.go.kr/{키}/waterlevel/info.json`(관측소 1,417개 + 주의/경보 수위 임계치)과 `/waterlevel/list/10M/{코드}/{시작}/{종료}.json`(10분 단위 수위). 전국 4대강 통합 제공 확인 → spec Open Question #6 해결. 홍수 이벤트는 "최신 수위 ≥ 임계치" 자체 판정으로 구현.

**설계 개선 두 가지.**
- ingest를 소스별 try/except로 격리 — 한 소스가 죽어도 나머지는 처리하고, 응답 `errors`에 소스별 에러를 노출. (한 데이터 소스 장애가 전체 파이프라인을 죽이면 안 된다는 기본기.)
- 테스트 격리 버그 발견·수정: `.env`에 실제 키가 생기자 테스트가 실 API를 호출하려다 실패. `tests/conftest.py`에서 키 환경변수를 비워 테스트는 항상 mock을 쓰게 고정. "테스트가 환경에 따라 다르게 도는" 전형적 함정.

**결과.** `POST /events/ingest` → `{"events_ingested": 8, "notifications_created": 0, "errors": {}}`. 실제 공공 API 3개 → 정규화 → Postgres 저장까지 전체 파이프라인이 처음으로 끝까지 돌았다. 알림 0은 특보 이벤트에 region이 아직 없어서(통보문 상세 연동 전)이며 예상된 동작.

### 2026-07-19 — 특보→지역 매칭, 실데이터 알림 생성 성공 🎉

**통보문 상세(getWthrWrnMsg) 연동.** 특보 클라이언트를 발표 이력 목록(getWthrWrnList)에서 통보문 상세 기반으로 전환. 핵심 발견: 최신 통보문의 `t6` 필드가 "이 시점 발효 중인 특보 전체 + 지역" 스냅샷이라, 이거 하나만 파싱하면 현재 상황을 다 얻는다.

**텍스트 파싱의 현실.** 지역이 구조화된 필드가 아니라 자연어에 가까운 텍스트로 온다: `충청남도(보령(도서제외), 보령도서)`, `제주도(제주도산지, 추자도 제외)`, `인천`(하위구역 없음). 괄호 깊이를 추적하는 스플리터(`_split_top_level`)를 직접 짜서 해결 — 중첩 괄호 한정어 제거('보령(도서제외)'→'보령'), '제외' 항목 스킵, 시도 단위는 sigungu='전체'. 실제 응답 케이스를 그대로 테스트로 박아뒀다(test_warning_msg_parser.py).

**이벤트 중복 방지(dedupe).** t6는 스냅샷이라 같은 특보가 매 사이클 반복 유입된다. (소스·종류·등급·지역·발표시각)이 같으면 기존 이벤트를 재사용하고 알림 평가를 건너뛰게 해서 중복 알림을 차단. 응답에 `duplicates_skipped`로 노출.

**끝까지 도는 순간.** 지역 생성 → 구독 생성 → ingest 순서로 실행하니:
`{"events_ingested": 63, "duplicates_skipped": 1, "notifications_created": 1}` →
`"[폭염특보] 전라남도 광양에 이상상황이 감지됐어요. 어머니님 관련 주의가 필요해요"` (HIGH, matrix).
**공공 API → 텍스트 파싱 → 지역 매칭 → 규칙 매트릭스 → 개인 맞춤 알림**까지, 프로젝트의 핵심 가설이 실데이터로 처음 검증됐다.

**과정에서 배운 것.** (1) 422 에러 = 요청 JSON 검증 실패 — placeholder를 실제 UUID로 안 바꾸면 난다. (2) "구독을 먼저, ingest를 나중에" — 알림 평가는 이벤트 생성 시점에만 돌기 때문. 이건 나중에 "구독 생성 시 기존 발효 특보 소급 평가" 기능으로 개선할 만하다(TODO). (3) 개발 중 데이터 리셋은 `docker compose exec db psql`로 직접 DELETE.

### 2026-07-19 — 구독 소급 평가 + 지역명 정규화

**소급 평가(backfill).** 위 (2)의 순서 문제를 바로 해결했다. 평가 로직을 `_notify_subscription_for_event()`(이벤트×구독 한 쌍 평가)로 추출해 ingest 경로와 공유하고, 구독 생성 시 최근 48시간 내 해당 지역 이벤트를 소급 평가하는 `backfill_subscription()`을 추가. 같은 (구독, 이벤트) 쌍 알림은 중복 생성하지 않는다. 검증: 순천 구독을 만들자 ingest 재실행 없이 즉시 폭염 HIGH 알림 생성 확인. **리팩터링 포인트: 같은 로직이 두 경로에서 필요해지면 복붙하지 말고 함수로 추출해 공유한다.**

**지역명 정규화.** 통보문은 '광양', 사용자는 '광양시'라고 쓸 수 있어 region 매칭이 깨질 수 있다. `normalize_sigungu()`로 단일 단어 시/군 접미사를 떼고 저장('광양시'→'광양'). 복합 표기('청주시 흥덕구')는 그대로. 근본 해결은 행정구역 코드 기반 매칭(TODO). **데이터 정합성 교훈: 같은 실체를 가리키는 표기가 여럿일 때는 "저장 시점 정규화"가 매칭 문제를 가장 싸게 막는다.**

### 2026-07-19 — Phase 2 시작: LLM 알림 문구 생성

**설계 원칙: fallback 필수.** 알림은 안전 기능이라 "LLM 장애 = 알림 불발"이면 안 된다. `app/services/message.py`: OpenAI(gpt-4o-mini)로 문구를 생성하되, 키 없음·호출 실패·빈 응답 어느 경우든 즉시 기존 템플릿으로 fallback. 이 구조 덕에 LLM 은 "있으면 좋은 것"이고 없어도 서비스는 완전하다.

**프롬프트 설계.** 시스템 프롬프트에 규칙을 명시: 2~3문장 120자 이내, 첫 문장에 상황+지역, 이어서 인물 특성(나이대·태그) 맞춤 행동 요령 1가지, 과장 금지, 이모지 금지. 이벤트·지역·위험도·인물 정보를 유저 프롬프트로 전달.

**테스트 전략.** 실제 OpenAI 를 호출하지 않고 `monkeypatch` 로 `httpx.post` 를 가짜로 바꿔 세 경로를 검증: 키 없음→템플릿, 정상 응답→LLM 문구 사용(+프롬프트에 인물 특성 포함 확인), 에러/빈 응답→fallback. **외부 API 의존 코드의 테스트는 "호출을 어떻게 속일까"가 핵심.**

**실전에서 겪은 것 두 가지.**
- 중복 구독 500: (person, region) 유니크 제약에 걸려 IntegrityError. `create_subscription` 을 get-or-create 로 바꿔 멱등(idempotent)하게 만들었다. **같은 요청을 두 번 보내도 같은 결과가 나오는 API 가 좋은 API.**
- `insufficient_quota`: OpenAI 는 선불 크레딧이 없으면 호출 거부 → fallback 이 실전에서 첫 작동. curl 로 원인 확인 → 크레딧 충전 → 재시도로 해결. fallback 이 있어서 이 장애 동안에도 알림은 정상 생성됐다.

**결과.** 템플릿: "[폭염특보] ... 주의가 필요해요 (severity=주의보)." →
LLM: "전라남도 순천에 폭염특보가 발효되었습니다. 어머니님은 외출 시 그늘을 찾고, 수분을 충분히 섭취해 주세요."
인물 특성 맞춤 행동 요령이 실데이터로 생성됨. Phase 2 첫 조각 완성.

### 2026-07-19 — LLM 프로바이더 폴백 체인 + 쿨다운

**동기.** 실제로 quota 소진(insufficient_quota)을 겪고 나니 "유료가 죽으면 무료 모델로 자동 전환"이 필요하다는 게 명확해졌다. 단순 if/else 가 아니라 실무 패턴으로 설계:

```
1순위: 유료 (OpenAI gpt-4o-mini)
  ↓ 실패 시
2순위: 무료 폴백 (.env 의 LLM_FALLBACK_* — Gemini 무료 티어 등)
  ↓ 실패 시
최종: 템플릿 문구 (알림은 반드시 나간다)
```

**핵심 설계 3가지.**
- **프로바이더 추상화**: OpenAI 호환 API(chat/completions)라는 공통 규격 덕에, 프로바이더를 (base_url, api_key, model) 세 값으로 일반화. Gemini·Groq·OpenRouter·로컬 Ollama 까지 .env 설정만으로 갈아끼울 수 있다. "고객사 보안 요건상 외부 API 금지 → 로컬 LLM 전환" 같은 FDE 시나리오에 그대로 대응.
- **쿨다운(서킷 브레이커 단순판)**: 401/402/429(키 문제·quota 소진)가 감지된 프로바이더는 15분간 시도 자체를 건너뛴다. 죽은 프로바이더에 매 알림마다 실패 호출을 반복하며 지연을 쌓지 않기 위함. 상태는 프로세스 메모리 — 다중 인스턴스 배포 시 Redis 등으로 옮겨야 한다는 한계도 기록.
- **에러 구분**: quota/인증 오류(지속적 → 쿨다운)와 네트워크 오류(일시적 → 쿨다운 없이 다음 프로바이더만)를 다르게 처리.

**테스트.** httpx.Response 객체를 직접 만들어 429 를 흉내내는 방식으로 4가지 시나리오 검증: 유료 429 → 무료가 문구 생성, 쿨다운 후 다음 알림에선 유료를 건너뜀(호출 횟수로 검증), 전부 실패 → 템플릿, 쿨다운 상태의 테스트 간 격리(autouse fixture).

**면접 한마디.** "LLM 의존 기능에 3단계 폴백 체인을 설계했습니다. 유료 quota 소진 시 무료 프로바이더로 자동 전환하고, 실패한 프로바이더는 쿨다운으로 격리하며, 최종적으로는 LLM 없이도 동작하는 템플릿을 둬서 안전 기능의 가용성을 보장했습니다."

**무료 폴백(Gemini) 실연동에서 배운 것.** aistudio.google.com 에서 무료 키 발급 → 처음 지정한 `gemini-2.0-flash` 는 429 에 `limit: 0` — "다 써서"가 아니라 **그 구세대 모델의 무료 티어 자체가 닫힌 것**. 429 응답을 읽는 법: `limit: 0` 이면 quota 소진이 아니라 할당 자체가 없다는 뜻이다. `GET /models` 로 사용 가능 모델을 조회해 `gemini-flash-lite-latest`("latest" 별칭이라 세대 교체에도 안 깨짐)로 바꿔 해결. 검증 순서도 교훈: 앱에 붙이기 전에 curl 로 (1) 모델 목록 (2) 최소 호출을 먼저 확인하면 디버깅이 빠르다.

### 2026-07-20 — 스케줄러: 10분 주기 자동 수집 + 중복 실행 가드

**설계가 곧 예산 집행.** 위 호출량 분석이 그대로 설계 근거가 됐다: 주기 10분(재난문자 한도의 14.4%), 수동 호출 가드 3분. 설정은 `.env`로 조정 가능(`INGEST_INTERVAL_MINUTES` 등)하되 기본값에 근거를 주석으로 박아뒀다(`app/config.py`).

**구현 선택: asyncio 백그라운드 태스크 (APScheduler 안 씀).** FastAPI 의 lifespan(서버 시작/종료 훅)에서 `asyncio.create_task`로 무한 루프를 띄우는 최소 구성(`app/scheduler.py`). 단일 프로세스 MVP 에선 라이브러리 하나 덜 쓰는 쪽을 택했고, 다중 인스턴스 배포 시엔 `SCHEDULER_ENABLED=0`으로 끄고 외부 스케줄러(Cloud Scheduler → POST /events/ingest)로 전환하는 퇴로를 문서화해뒀다. 주의점 하나: ingestion 코드가 동기(sync)라 이벤트 루프를 막지 않게 `asyncio.to_thread`로 스레드에서 실행.

**중복 실행 가드.** `run_ingestion_cycle_guarded()` — 마지막 실행 시각(모듈 전역)을 기억해서, 최근 N분 내 재호출이면 공공 API 를 건드리지 않고 `{"skipped": true, "reason": ...}` 반환. 스케줄러와 수동 `/events/ingest`가 같은 가드를 공유하므로 겹쳐도 안전하다. LLM 쿨다운(밤 폴백 체인)과 같은 패턴 — "상태 기억해서 낭비 호출 차단"이 이 프로젝트의 반복 모티프가 됐다.

**루프 생존성.** 사이클 전체가 실패해도(DB 다운 등) 루프는 `try/except`로 살아남아 다음 주기에 자연 재시도. 10분 주기 자체가 완만한 백오프 역할. 소스별 실패는 기존대로 격리·기록된다.

**테스트 격리 추가.** conftest 에 `SCHEDULER_ENABLED=0` — 테스트 중 백그라운드 폴링이 돌면 타이밍 비결정성이 생기니 원천 차단. 가드 로직은 별도 단위 테스트 4개로 검증(`test_scheduler_guard.py`), 스모크로 "서버 기동 → 자동 수집 → 수동 재호출 skipped → 종료 정리"까지 확인.

**면접 한마디.** "폴링 주기를 감으로 정하지 않고, 소스별 API 한도를 조사해 호출량 예산을 계산한 뒤 그 근거로 10분 주기와 중복 실행 가드를 설계했습니다."

### 2026-07-20 — 로그 시크릿 마스킹

**발견.** 스케줄러 실기기 검증 로그를 보다가, httpx 가 요청 URL 전체를 INFO 로 찍으면서 **API 키가 로그에 그대로 노출**되는 걸 발견 — 공공 API 는 serviceKey 를 쿼리스트링에, 홍수통제소는 URL 경로에 키를 넣는 구조라 피할 수 없다. 로컬에선 무해하지만 배포 후 로그 수집 시스템에 키가 쌓이면 유출 경로가 된다. **시크릿 관리는 .env 만으로 끝나지 않는다 — 로그도 유출 채널이다.**

**해결.** 로그를 끄는 대신(요청 로그는 디버깅에 유용) 루트 로거 핸들러에 `SecretRedactionFilter` 를 달아 설정의 모든 시크릿 값을 `***REDACTED***` 로 치환(`app/logging_utils.py`). httpx 같은 서드파티 로거는 루트로 전파되므로 루트 핸들러 필터 하나로 전부 커버된다. 디테일 두 가지: (1) 8자 미만 값은 오탐(평범한 단어까지 가림) 방지를 위해 제외, (2) 새 시크릿이 설정에 추가되면 자동으로 마스킹 대상에 포함.

**면접 한마디.** "시크릿 유출 채널을 저장소(.env/gitignore)뿐 아니라 로그까지 넓혀 봤습니다. 서드파티 라이브러리가 URL 을 로깅하며 키를 노출하는 걸 발견하고, 루트 로거 필터로 알려진 시크릿을 자동 마스킹했습니다."

### 2026-07-20 — Layer 2: LLM 위험도 보조 판단 (Phase 2 완결)

**흐름 완성.** spec 4절의 2계층 설계가 드디어 코드로 완성됐다: Layer 1 규칙 매트릭스가 못 잡는(None) 케이스 — 예: 한파경보 + 특이 태그 없는 성인 — 를 LLM 이 판단하고, 결과가 MEDIUM/HIGH 면 `risk_source=ai` 알림 생성, 모든 판단은 `ai_risk_logs` 에 기록(왜 알림을 보냈/안 보냈는지 감사 가능).

**설계 결정 4가지.**
- **리팩터: LLM 체인 범용화.** 문구 생성 안에 있던 폴백 체인을 `app/services/llm.py`(`chat(system, user)`)로 분리 — 문구 생성과 위험도 판단이 같은 체인·쿨다운을 공유한다. "두 번째 소비자가 생기면 추출한다" 원칙.
- **판단 보류 ≠ 기본값.** LLM 실패나 형식 위반 응답이면 None(보류) — 규칙에 없는 케이스를 임의로 HIGH 처리하면 오탐, LOW 처리하면 미탐이라 어느 쪽 기본값도 위험하다. 보류하면 다음 사이클에 자연 재시도된다.
- **LOW 는 기록만, 알림은 안 보냄.** 알림 피로(fatigue)는 안전 서비스의 적 — 프롬프트에도 "애매하면 낮은 쪽"을 명시.
- **판단 캐시.** 같은 (이벤트유형·등급·나이대·태그) 조합은 인물이 달라도 같은 판단이므로 메모리 캐시. 전국 특보 × 다수 구독자에서 LLM 호출 폭증 방지 (기록은 구독별로 전부 남긴다).

**구조화 출력 파싱.** "첫 줄에 HIGH/MEDIUM/LOW, 둘째 줄에 근거 한 문장" 형식을 시스템 프롬프트로 강제하고, 정규식으로 레벨 토큰을 뽑는다. 형식 위반 응답은 판단 보류로 처리 — LLM 출력을 그대로 믿지 않고 항상 검증한다.

**면접 한마디.** "결정론적 규칙을 1차 안전망으로 두고, 규칙 밖 케이스만 LLM 에 보조 판단을 맡기는 하이브리드입니다. LLM 실패 시 판단 보류(기본값 판정 금지), LOW 필터로 알림 피로 방지, 프로필 캐시로 호출 비용 통제, 전 판단 감사 로그까지 — 신뢰성 요건을 먼저 정하고 LLM 을 그 안에 가뒀습니다."

**실데이터 실증 (scripts/demo_layer2.py).** 경북 의성(호우+폭염 동시 발효)에 태그 없는 성인을 구독시키자, 한 알림 목록에 두 계층이 나란히 나타났다:
- 폭염특보 → `[MEDIUM/matrix]` (규칙이 잡음 — LLM 안 감)
- 호우특보 → `[MEDIUM/ai]` (규칙에 없음 — LLM 판단, 근거: "주의가 필요하지만 특별한 조치 없이도 상황을 관리할 수 있다")
ai_risk_logs 에 같은 근거 문장이 반복된 것으로 캐시 작동도 확인(같은 프로필 조합 → LLM 재호출 없이 기록만 추가). 처음 잘못 짚었던 것도 기록: 데모 첫 시도에서 ai_risk_logs 가 0건이었는데, 이는 실패가 아니라 그 지역 특보(폭염)가 규칙에 있어서 Layer 2 까지 갈 필요가 없었던 것 — **"발동 안 함"과 "고장"을 구분하려면 어느 계층이 잡았는지(risk_source)가 보여야 한다**는 관측 가능성 교훈.

### 2026-07-22 — 긴급재난문자 연동 (Option A: 공식 방송 취급)

**프로브 먼저 — 두 미해결을 실측으로 풀었다.** 학습노트에 "날짜 필터 파라미터 확인 필요"로 남겨둔 항목이 있었다. 코드부터 짜지 않고 포커스 프로브(오늘/어제 crtDt로 3콜)를 먼저 돌렸더니 두 가지가 한 번에 풀렸다: (1) **날짜 필터 = `crtDt`(YYYYMMDD)** — 지정한 날의 문자만 반환. (2) 최신 데이터를 보니 **필터 정책의 전제가 바뀌었다** — `EMRG_STEP_NM`은 폭염·호우·댐방류까지 전부 "안전안내"라 필터 기준으로 무용지물이고, **실제 판별자는 `DST_SE_NM`(재난구분)**이었다. 2023년 덤프(실종자 위주)만 봤으면 못 잡았을 사실. **"추정 대신 실측"이 또 한 번 스펙을 바로잡았다.**

**응답 구조가 data.go.kr과 다르다.** safetydata는 `header`/`body`가 최상위(`response.` 하위 아님)고 `body`가 리스트 그 자체다(`{"item":[...]}` 래핑 없음). 소스마다 응답 관례가 달라서, 정규화 계층(`NormalizedEvent`)이 이 차이를 흡수해주는 설계의 값어치가 다시 확인됐다.

**최신을 얻으려 마지막 페이지를 본다.** 정렬이 SN 오름차순(오래된 순)이라 `pageNo=1`은 그날 가장 오래된 문자가 나온다. 그래서 **2-call 방식**: (1) `numOfRows=1`로 총건수만 확인 → (2) `last_page = ceil(total/100)` 페이지를 가져와 최신 ≤100건. 10분 주기 × 하루 볼륨(어제 178건)이면 한 번도 놓치지 않는다. 호출량은 288회/일로 일일 한도 1,000의 28.8% — 재난문자가 가장 빡빡한 소스라(타 소스 10,000, 이건 1,000) 이 계산을 먼저 하고 설계했다.

**필터: 화이트리스트가 아니라 denylist.** "재해만 남기자"는 같은 목표라도 구현이 둘이다. 화이트리스트(폭염·호우·…만 통과)는 목록에 없는 **신규 재난 유형을 조용히 놓치는 false negative** 위험이 있다 — 안전 서비스에선 최악의 실패 유형. 그래서 **알려진 비재해(`기타`=실종자·물놀이안내, `교통통제`)만 제외하는 denylist**로 갔다. 실증에서 정당성이 드러났다: 오늘치 90건에 `산사태·화재·붕괴·홍수`가 섞여 있었는데, 화이트리스트였다면 이걸 일일이 명시해야 했고 하나만 빠뜨려도 놓쳤을 것. denylist는 신규 재해를 자동 포함했다.

**Option A — 상류의 판단을 신뢰하고 재판정하지 않는다.** 다른 소스(기상특보·지진·홍수)는 "원시 신호 → 우리가 위험도 판정"이지만, 재난문자는 **이미 당국이 '이 지역에 방송할 가치가 있다'고 판정해 완성한 경보**다. 그걸 규칙/LLM으로 다시 판정하는 건 (a) 개념적으로 상류 판단의 중복이고 (b) 폭염/호우는 기상특보 소스와 중복 알림 위험이며 (c) Layer 2 캐시 키가 `(event_type, severity, …)`라 event_type이 전부 '긴급재난문자'·severity가 전부 None인 재난문자에선 **서로 다른 문자가 캐시 충돌**하는 버그까지 유발한다. 그래서 필터 통과 = 관련 있음으로 보고 `risk_source=broadcast`/MEDIUM을 매기고, **개인화는 위험도가 아니라 문구에서** 한다 — 사용자가 실제로 보는 푸시 텍스트에 당국 원문(`MSG_CN`)을 넣고 기존 문구생성 LLM이 인물 특성에 맞춰 다듬는다. "실제 메시지를 읽는" 이득은 정작 중요한 곳(사용자가 보는 텍스트)에서만 챙기고, 위험판정 LLM 호출은 0으로.

**호출량을 먼저 따졌다(Option 선택의 근거).** 사용자가 "Layer 2 LLM 개인 맞춤으로 가면 호출량이 얼마냐"고 물어서 계산해보니, MVP에선 ~5~20건/일(대부분 문자가 구독자 0인 지역이라 평가 자체가 안 돎), 전국 커버 시에도 `재해문자 × 지역별 프로필조합`으로 bounded였다. 무시 가능한 수준이지만, 문구가 이미 개인화되는 이 서비스에서 위험판정까지 LLM에 맡기는 추가 가치가 작고 캐시 버그까지 떠안아야 해서 Option A가 더 맞다고 판단했다. **"호출량 예산을 먼저 계산하고 설계를 정한다"가 또 작동했다.**

**지역 파싱의 현실(또again).** `RCPTN_RGN_NM`은 "시도 시군구 [읍면동]" 공백 구분에 쉼표로 다지역. 시도만 오면(`울산광역시`) sigungu='전체', 시+구 복합(`고양시 덕양구`)은 통째로 유지, 동 단위(`강남구 역삼동`)는 버리고, 쉼표 중복(`경기도 임진강 ,경기도 임진강`)은 제거. 특보 t6 파싱과 같은 계열의 텍스트 정규화 작업. 한 문자가 여러 지역이면 지역별 이벤트로 분리(특보와 동일 패턴).

**검증.** 단위/통합 테스트 10개 추가(테스트 57개로) — 지역 파싱 5종, crtDt 파싱, denylist+최신페이지+지역확장(httpx monkeypatch), 빈 날, 파이프라인 broadcast 알림. 그리고 **실데이터 실증**: 실제 API에 붙여 오늘치 90건 정규화 확인(폭염 46·호우 35·산사태 5·화재 2·붕괴 1·홍수 1), denylist가 기타·교통통제만 정확히 제거하고 지역 파싱도 실데이터에서 정상.

**면접 한마디.** "재난문자는 당국이 이미 완성한 경보라, 위험엔진으로 재판정하지 않고 '상류 판단 신뢰 + 개인화는 문구에서'로 설계했습니다. 필터는 신규 재난을 놓치지 않도록 화이트리스트가 아닌 denylist를 택했고, API 스펙은 추정 대신 프로브로 실측해 날짜 필터와 실제 판별 필드(EMRG_STEP이 아닌 DST_SE)를 바로잡았습니다."

### 2026-07-22 — 홍수통제소 호출 스로틀링 (분당 한도 방어)

**왜 지금.** 호출량 예산 분석(2026-07-20)에서 병목 3개를 짚었는데, 그중 하나가 "홍수통제소 분당 1,000 제한 — 관측소 동적 선정 시 순간 초과하면 키 차단(3회)"이었다. 관측소 동적 선정 기능을 켜기 **전에** 안전장치를 먼저 깔아두는 게 순서다(기능을 켜고 나서 차단당하면 늦다).

**일일 한도와 분당 한도는 통제 수단이 다르다.** 일일 한도는 폴링 주기로 막지만(하루 총량), 분당 한도는 폴링 주기로 못 막는다 — 한 사이클 안에서 관측소 N개를 순회하면 그 **순간의 호출 속도**가 문제이기 때문이다. `INGEST_INTERVAL_MINUTES`를 아무리 늘려도 한 사이클이 순식간에 1,000콜을 쏘면 차단된다. 그래서 **주기와 별개로 사이클 내부의 호출 속도에 상한**을 걸어야 한다.

**순차 호출만으로는 부족하다(핵심).** "병렬을 순차로 바꾸면 되지 않나"가 첫 직관인데, 순차라도 각 호출이 빠르면 속도가 한도를 넘는다: N=1,417 관측소 × 콜당 50ms = 분당 약 1,200콜 > 1,000. 속도 자체에 바닥(최소 간격)을 깔아야 한다.

**구현: 최소 간격 게이트.** `hrfco_flood.py`에 `_RateLimiter`를 넣고, 모든 outbound 호출(관측소 목록 1콜 + 관측소별 수위 N콜) **직전에 `wait()`**를 붙였다. `분당 최대 M회 → 최소 간격 60/M초`. 직전 호출로부터 그만큼 안 지났으면 `sleep`한다. 상한은 한도의 60%인 **분당 600(콜당 0.1초)** — N이 아무리 커도 절대 한도를 못 넘는다. 설정 `HRFCO_MAX_REQUESTS_PER_MINUTE`로 조정 가능(config에 근거 주석 박음). 이건 스케줄러 중복 가드·LLM 쿨다운·이벤트 dedupe와 같은 **"상태(직전 호출 시각)를 기억해 낭비/위험 호출을 막는다"** 모티프의 반복이다.

**설계상 스코프.** 분당 제한 + 사이클당 N콜 패턴은 홍수통제소에만 해당한다(타 소스는 사이클당 1~2콜). 그래서 `base.py`(공통)가 아니라 `hrfco_flood.py`에만 두는 게 surgical하다 — 필요 없는 소스에 오버헤드를 안 준다.

**테스트: 실제 대기 없이.** 리미터에 가짜 시계(`monotonic`)와 `sleep`을 **주입**해, 진짜로 자지 않고 결정론적으로 검증했다(스케줄러 가드가 모듈 전역 시각을 fixture로 리셋한 것과 같은 계열). 검증 항목: 즉시 연속 호출 시 0.1초씩 대기, 간격이 충분하면 대기 안 함, 600회 호출 시 총 59.9초로 눌림(한도 준수), 클라이언트가 매 outbound 호출 앞에 게이트를 통과(목록1+수위2=3콜↔wait 3회). 테스트 5개 추가(62개로).

**면접 한마디.** "일일 한도는 폴링 주기로, 분당 한도는 클라이언트 사이드 레이트 리미터로 통제했습니다. 순차 호출이라도 속도가 한도를 넘을 수 있어 호출 직전 최소 간격 게이트로 속도 자체에 상한을 걸었고, 관측소 동적 선정을 켜기 전에 안전장치를 먼저 깔았습니다. 리미터에 시계·sleep을 주입해 실제 대기 없이 테스트했습니다."

### 2026-07-22 — FCM 웹푸시 발송 (생성/발송 분리 + v1 서비스계정)

**시작점.** 모델(`device_tokens`, `notifications.sent_at`)은 이미 있었지만 실제 발송이 없어, 알림이 DB에 `sent_at=NULL`로 쌓이기만 하고 아무 데도 안 나갔다(`ingest.py`에 `TODO: 실제 발송`). 그걸 채웠다.

**아키텍처 결정: 생성과 발송을 분리(사용자와 상의).** 인라인 발송(알림 만들 때 바로 FCM 호출) 대신 **별도 dispatch 단계**를 택했다. 근거: 이미 있는 `sent_at` 컬럼이 자연스러운 "발송됨" 표식이고, 이걸 가드로 쓰면 (1) 중복발송 방지(성공분 재발송 안 함), (2) 실패 자동 재시도(sent_at 안 찍으면 다음 사이클에 다시), (3) 위험판정·문구생성과 전송의 관심사 분리가 공짜로 딸려온다. 이 프로젝트의 "상태 기억으로 낭비/중복 호출 차단" 모티프와 정확히 같은 결.

**FCM v1 = 서비스계정 OAuth2.** 레거시 서버키는 2024.6 폐기라, 서비스계정 JSON으로 단명 액세스 토큰을 발급(`google-auth`가 자동 갱신)해 Bearer로 붙이는 v1 엔드포인트(`/v1/projects/{id}/messages:send`)로 구현했다. 폐기된 `fcm_server_key` 설정을 제거하고 `fcm_project_id`+`fcm_credentials_file`(env 관례명 `GOOGLE_APPLICATION_CREDENTIALS`)로 교체, 로그 마스킹 목록도 정리.

**graceful degradation(또).** 서비스계정 JSON이 아직 없어서 실제 FCM으로 못 쏴본다. 그래서 ingestion 클라이언트의 mock 패턴을 그대로 가져와, 자격증명이 없으면 발송을 no-op(status=mock)로 처리했다. 덕분에 "토큰 등록 → 알림 생성 → dispatch"가 로컬에서 끝까지 돌고, 나중에 `secrets/`에 JSON만 넣으면 실발송으로 자동 전환된다. `google-auth`/`requests`는 실발송 경로에서만 지연 import라 미설정 환경에선 없어도 앱이 뜬다.

**죽은 토큰 위생.** FCM이 404(UNREGISTERED)를 주면 그 토큰은 죽은 것(앱 삭제·구독 해제)이라 dispatch가 즉시 삭제한다. 반대로 400/5xx 등은 일시 오류로 보고 토큰을 남겨 재시도한다 — 우리 쪽 요청 버그로 멀쩡한 토큰을 지우는 사고를 피하려고 "지우는 신호"를 404로만 좁혔다.

**함정: conftest가 FCM도 꺼야 했다.** end-to-end 테스트가 처음에 실패했는데, 원인은 내 `.env`에 `FCM_PROJECT_ID`/`GOOGLE_APPLICATION_CREDENTIALS`가 채워져 있어 테스트에서 client가 enabled로 뜨고 실제 서비스계정 파일을 찾다 error가 난 것. 2026-07-17의 "API 키 격리 버그"와 판박이 — **테스트는 실제 자격증명·네트워크 없이 돌아야 한다**는 원칙에 따라 conftest의 격리 목록에 FCM 두 변수를 추가했다.

**검증.** 테스트 11개 추가(73개로) — 전부 실제 FCM·네트워크 없이(mock + 주입 클라이언트 + httpx monkeypatch). `POST /device-tokens`(멱등 등록) 엔드포인트 + crud도 추가. 실발송 경로는 `google-auth` 설치 후 "파일 없음도 예외 없이 error로 degrade"까지 확인(실제 FCM 대상 발송은 서비스계정 JSON 발급 후 실기기에서 검증 예정).

**면접 한마디.** "생성과 발송을 분리해 sent_at을 멱등 가드로 삼았고, FCM은 폐기된 서버키 대신 서비스계정 OAuth2 v1으로 붙였습니다. 자격증명이 없으면 no-op로 degrade해 파이프라인 전체를 자격증명 없이 테스트했고, 죽은 토큰은 404에서만 정리해 오삭제를 막았습니다."

### 2026-07-22 — 웹 PWA 구독 화면 (프론트 최소 구성)

**시작점.** 백엔드 파이프라인(수집→매칭→위험도→알림 생성→발송)은 완성됐지만 사용자가 만질 화면이 없었다. 구독을 만들려면 /docs에서 API를 직접 눌러야 했고, FCM 웹 토큰을 발급받을 클라이언트도 없었다.

**스택 결정(사용자와 상의): 빌드 도구 없는 정적 서빙.** React/Vite 별도 앱 대신 `app/static/`에 순수 HTML+JS를 두고 FastAPI가 서빙(`GET /app`)하는 최소 구성을 택했다. 근거: MVP에서 필요한 화면은 폼 몇 개라 프레임워크가 과하고, Node 툴체인·CORS·빌드 파이프라인을 안 들여오면 uvicorn 하나로 전부 돈다. Firebase SDK는 "알림 켜기"를 누를 때만 CDN에서 동적 import(첫 화면을 가볍게). JWT도 뒤로 미루고 기존 `user_email` 임시 방식을 그대로 썼다 — 화면이 먼저 보이는 게 학습에도 동기부여에도 낫다는 판단.

**화면 흐름.** 이메일 → 보호 대상 등록(연령대·태그는 백엔드 enum과 동일 값) → 지역 구독(region get-or-create 후 subscription 생성, 직후 backfill로 생긴 알림도 바로 표시) → "알림 켜기"(권한 요청→SW 등록→FCM 토큰 발급→`POST /device-tokens`) → 알림 내역.

**서비스워커를 동적 생성한 이유.** FCM 백그라운드 수신용 `firebase-messaging-sw.js`는 페이지와 별개 파일이라 설정을 전달받기 어렵고, 파일에 하드코딩하면 설정이 코드에 흩어진다. 그래서 라우트가 `.env`의 `FCM_WEB_*` 값을 주입한 JS를 생성해 서빙했다. SW scope 규칙(서빙 경로 이하만 제어) 때문에 루트 경로 서빙이 필요한데, 라우트 방식이면 이것도 자연스럽다. 웹 클라이언트 설정은 브라우저에 공개되는 값이라 시크릿은 아니지만, 설정을 `.env` 한 곳에 모으는 기존 습관을 유지했다.

**graceful degradation(또또).** `GET /firebase-config`가 미설정이면 `enabled=false` — 프론트는 "알림 켜기"만 비활성화하고 안내 문구를 띄우며, 구독 관리는 전부 동작한다. 실제로 아직 Firebase 웹 앱 설정을 발급 안 받은 상태라, 이 degrade 경로가 현재의 기본 동작이다.

**검증.** pytest 6개 추가(79개로): 화면·정적 파일 서빙, firebase-config 미설정/설정 분기, SW 404/설정 주입. 브라우저에서도 실제로 이메일→보호 대상(어머니·고령·보행보조필요)→구독(충청북도 청주시 흥덕구) 생성까지 눌러서 확인했다(DB에 실제 저장됨). FCM 토큰 발급 실검증은 Firebase 콘솔에서 웹 앱 등록+VAPID 키 발급 후.

**면접 한마디.** "MVP 프론트는 빌드 도구 없이 FastAPI 정적 서빙으로 백엔드와 한 프로세스에 담았습니다. FCM 서비스워커는 설정 하드코딩 대신 서버가 .env 값을 주입해 동적 생성했고, Firebase 설정이 없으면 알림 기능만 꺼지는 degrade 경로를 기본으로 두어 설정 발급 전에도 전체 화면이 동작합니다."

### 2026-07-23 — 알림 dedupe: 통보문 시그니처로 분할 구역 합치기

**문제.** 실기기 검증에서 발견한 UX 문제 — 기상특보 통보문 하나가 예보구역 수만큼 이벤트로 쪼개져(경주 폭염 → 남부/서부/동부/중북부 = 4건), 같은 특보인데 푸시가 4번 왔다.

**키 설계가 핵심.** 처음 아이디어는 "같은 사이클의 (보호대상, 특보 종류·등급)은 1건"이었는데, 구현하며 더 정확한 기준을 찾았다. 분할 구역 이벤트들은 전부 **같은 통보문**에서 나오므로 `(source, event_type, severity, occurred_at=발표시각)`이 완전히 같고 region만 다르다. 그래서 "사이클"이라는 임의 경계 대신 **(보호 대상, 통보문 시그니처)당 알림 1건**으로 잡았다 — 분할 이벤트가 사이클 경계에 걸쳐 나눠 들어와도 안전하고, 새 통보문(발표시각 변경)이면 다시 알림이 나간다.

**결정 2가지.**
- **기상특보에만 적용.** 재난문자는 같은 시각에 발송돼도 문자 내용(MSG_CN)이 제각각이라 합치면 정보가 유실된다. 지진·홍수는 애초에 구역 분할이 없다. 문제가 실재하는 소스에만 건다.
- **위험도 평가보다 앞에서 자른다.** 중복 건이 Layer 2 LLM까지 가면 LLM 호출이 낭비된다. dedupe 가드를 매트릭스/LLM 평가 앞에 둬서 "상태를 기억해 낭비 호출을 막는" 프로젝트 모티프를 그대로 따랐다.

**구현.** `_notify_subscription_for_event`에 가드 하나 추가 — 같은 보호 대상(person_id)의 기존 알림 중 이벤트 시그니처가 같은 게 있으면 skip. Notification→Subscription→Event 조인 쿼리 하나로 끝. 생성 경로(ingest)와 소급 평가(backfill)가 이 함수를 공유하므로 양쪽 다 자동 적용된다. 부수 효과로 한 보호 대상이 겹치는 구독(경주시 + 경북 전체)을 가져도 1건만 온다. 테스트 6개 추가(100개로): 분할 4구역→1건, 새 통보문→새 알림, 보호대상별 독립, 겹치는 구독, 재난문자 미적용, backfill 경로.

**면접 한마디.** "중복 제거는 '무엇이 같으면 중복인가'라는 키 설계가 전부입니다. 임의 경계(폴링 사이클) 대신 데이터의 자연 키(통보문 발표시각 시그니처)로 잡아 경계 문제를 없앴고, 가드를 LLM 평가 앞에 둬 비용도 같이 아꼈습니다."

### 2026-07-23 — 인증 전환: 구글+카카오 소셜 로그인 + JWT 30일 + 보호 대상 상한

**설계 논의가 절반이었다.** 처음 아이디어는 "핸드폰번호 + 6자리 PIN + 기기 고유값"(은행 앱 모델)이었는데, 조사해 보니 **모바일 웹에서는 기기 고유값을 얻을 수 없다** — 브라우저가 추적 방지를 위해 하드웨어 식별자를 의도적으로 막고, localStorage UUID·핑거프린팅은 지우거나 위조 가능해 보안 근거가 못 된다. PIN 의 약함을 기기 값이 보완하는 3각 구조가 웹에선 무너지는 것. 대신 두 가지 통찰로 방향을 틀었다: ① **"무분별한 구독"은 인증이 아니라 쿼터가 막는다** (정당한 1계정이 구독 1,000개 만드는 건 인증 강도와 무관 — 실제 보호 대상 자원은 구독 수에 비례하는 LLM 호출) ② 접근성(타겟: 4050 부모님·3040 자녀·1020 애인 구독)은 **소셜 로그인**이 최강 — 탭 한 번, 비밀번호 없음, 비용 0원, SMS 인증 불필요.

**구글+카카오 병행 근거.** 구글은 카톡 인앱 브라우저(웹뷰)에서 OAuth 를 차단(`disallowed_useragent`)하는데, 우리 유입 경로는 "카톡으로 공유받은 링크"가 주력일 것 — 카카오 로그인이 그 구멍을 메운다(자사 앱이라 인앱에서 잘 됨). 이메일은 안 받는다: 카카오는 비즈 앱 전환이 필요하고, 식별은 프로바이더 회원번호로 충분하며, 이메일 기반 자동 계정 통합은 탈취 벡터다. 같은 사람이 두 프로바이더로 가입해 계정 2개가 생기는 문제는 localStorage `last_provider` 로 "지난번에 이 방법으로 로그인했어요" 배지를 띄워 완화(같은 기기 한정).

**구현.** ① users 를 `(auth_provider, provider_user_id)` 쌍 유니크로 개편 + `person_limit`(기본 3 — 초과 시 409, 추후 유료 쿠폰이 올리는 구조) — Alembic 0002, 실제 Postgres 적용 확인. ② `/auth/{google,kakao}/login·callback` 서버사이드 code 흐름 + state 쿠키(CSRF) + 30일 HS256 JWT(`app/services/auth.py`) + `get_current_user` 의존성으로 라우트 4개의 `user_email` 파라미터 제거. ③ 화면 분리: `/login`(소셜 버튼 2개+배지) / `/app`(구독 설정+현황, 사용자 바+로그아웃) — 콜백이 `#token=` fragment 로 토큰을 넘기고 프론트가 저장 후 주소창에서 지운다. 테스트 122개(+16): 토큰 위조/만료, 보호 라우트 401, 상한 409, 콜백 흐름(구글 aud 검증 포함, httpx 모킹), 사용자 간 데이터 격리. 브라우저 검증: 토큰 없이 /app→/login 리다이렉트, fragment 핸드오프→"형인님 (카카오 로그인)" 표시, 로그아웃→배지 표시까지 확인.

**실검증까지 완료 (같은 날 저녁).** 구글·카카오 콘솔을 실제로 설정하고 실계정 로그인을 양쪽 다 검증했다 — DB 에 google/Peter JU, kakao/주형인 두 계정이 설계대로 별개 생성. 과정에서 만난 실전 이슈 3개: ① 카카오 콘솔이 개편되면서 Redirect URI 등록 위치가 "카카오 로그인 > 일반"에서 **앱 키(REST API 키)별 설정**으로 이동 — 구 가이드가 전부 낡은 상태라 데브톡 공식 답변으로 확인 ② "로그아웃 리다이렉트 URI"(고급 메뉴)에 잘못 등록해 KOE006 — 이름이 비슷한 다른 설정이었다 ③ 새 콘솔은 Client Secret 이 기본 활성이라 토큰 교환이 KOE010(invalid_client)으로 거절 — 에러 응답 로깅을 먼저 심어 원인 코드를 확보한 뒤 `.env` 에 KAKAO_CLIENT_SECRET 추가로 해결. ### 2026-07-27 — 인앱 브라우저 감지: 카톡에서 열면 안 되는 문제를 사용자에게 설명하기

**왜 이걸 먼저 했나.** 남은 일 중 가장 작은 작업이지만, 막고 있는 게 **첫 사용자의 첫 화면**이었다. 이 서비스의 유입 경로는 "카톡으로 부모님께 링크 보내기"인데, 카톡 인앱 브라우저에서는 구글 로그인이 정책상 거부되고(`disallowed_useragent`) 웹푸시 등록도 막힐 수 있다. 즉 링크를 그냥 누른 사람은 **아무 설명 없이 실패**를 본다 — 기능이 아무리 많아도 여기서 이탈하면 0이다. 클라우드 배포(더 큰 작업)보다 이걸 먼저 둔 이유.

**감지의 성격: 신뢰도 낮은 신호를 다루는 법.** "지금 인앱인가"를 알려주는 표준 API 는 없어서 User-Agent 문자열 패턴에 의존해야 한다(앱들이 UA 에 `KAKAOTALK`, `Instagram` 등을 덧붙이는 관행). 이런 추측성 신호에서는 **오탐이 미탐보다 비싸다** — 정상 크롬 사용자에게 "이 브라우저에선 안 돼요" 경고를 띄우는 건 없는 것보다 나쁘다. 그래서 ① 앱 이름이 UA 에 분명히 박히는 6종만 잡고 ② 안드로이드 웹뷰 일반 표식(`; wv`)처럼 모호한 건 **일부러 안 잡고** ③ 정상 브라우저 6종이 안 걸리는지 회귀 테스트로 고정했다. 특히 네이버 웨일은 UA 에 `NAVER` 가 들어가므로 패턴을 `NAVER(inapp` 으로 좁혔다 — 이런 게 실제로 사용자를 잃는 종류의 버그다.

**탈출은 앱마다 다르다.** 카카오톡은 커스텀 스킴(`kakaotalk://web/openExternal?url=...`), 라인은 쿼리 파라미터(`openExternalBrowser=1`)를 제공하지만 인스타·페이스북은 표준 방법이 없다. 그래서 배너 버튼을 두 종류로 두고 감지 결과에 따라 하나만 보여준다 — 방법이 있으면 "Chrome·Safari 로 열기", 없으면 "주소 복사하기"(클립보드 API 실패 시 주소를 화면에 노출하는 폴백까지). **graceful degradation** 모티프를 UI 에도 적용한 셈.

**JS 로직도 테스트한다.** 감지 규칙표는 클라이언트 JS 라 pytest 가 직접 못 돌린다. 그래서 `inapp.js` 를 **불러와도 아무 일도 하지 않는 모듈**로 설계하고(DOM 접근은 함수 안에서만), node 로 소스를 실행해 UA 12종을 표로 검증했다. node 가 없으면 skip 처리 — 이 테스트 때문에 프로젝트가 node 의존이 되면 안 되니까. 배너 마크업 자체는 기존 방식대로 서빙 테스트로 확인. 함정: 브라우저는 확장자와 무관하게 ES 모듈로 읽지만 node 는 `package.json` 없는 `.js` 를 CommonJS 로 봐서 `import` 가 실패한다 → 테스트는 소스를 이어붙여 실행한다.

**곁가지로 잡은 시간 폭탄.** 전체 테스트를 돌렸더니 dedupe 테스트 1건이 실패했다. 원인은 내 변경이 아니라 **테스트에 절대 날짜를 박아둔 것**(`ISSUED_AT = 2026-07-22`) — `backfill_subscription` 은 최근 48시간 이벤트만 소급 평가하므로, 작성 당일엔 통과하고 5일 뒤엔 창 밖으로 밀려나 깨진다. 실행 시각 기준 상대값(`now - 12h`)으로 고쳤다. 교훈: **시간 창을 가진 로직의 테스트에 절대 시각을 쓰면 안 된다.**

**검증.** 브라우저에서 UA 를 위조해 3가지 경로를 확인 — 정상 UA면 배너 없음, 카카오톡 UA면 "Chrome·Safari 로 열기", 인스타그램 UA면 "주소 복사하기". 테스트 128개 통과(+6). **실제 카카오톡 인앱에서의 확인은 같은 날 밤 클라우드 배포 후 완료** — 카톡으로 링크를 보내 열자 배너와 "Chrome·Safari 로 열기" 버튼이 그대로 떴다(당일 실배포 항목 참고).

**면접 한마디.** "추측성 신호(User-Agent)를 다룰 땐 오탐과 미탐의 비용을 먼저 비교했습니다. 정상 사용자에게 잘못된 경고를 띄우는 게 더 비싸다고 보고 규칙을 좁게 잡은 뒤, 오탐 회귀 테스트로 고정했습니다. 클라이언트 JS 도 부수효과 없는 모듈로 설계해 node 로 규칙표만 실행하는 식으로 테스트 범위에 넣었습니다."

### 2026-07-27 — 클라우드 배포 준비: 코드가 깔고 있던 가정 두 개를 꺼내 검사하기

**어디에 배포할지가 아키텍처 질문이었다.** 처음 후보는 Railway(가장 쉬움, 월 $5), Fly.io, Cloud Run + Cloud Scheduler 셋이었다. 그냥 "제일 쉬운 데"로 갈 수도 있었지만, 셋의 차이가 단순 비용·난이도가 아니라 **"주기 실행을 어디에 두는가"** 라는 설계 차이라는 걸 정리하면서 방향이 바뀌었다. Railway·Fly 는 상시 프로세스라 지금의 인프로세스 asyncio 루프를 그대로 쓸 수 있고, Cloud Run 은 요청이 없으면 프로세스가 사라지므로 **시계를 앱 밖으로 빼야 한다**. 그런데 그 "빼야 한다"는 제약이 실은 **개선**이었다 — 이유는 아래 두 가정에 있다. 그래서 더 어려운 쪽(Cloud Run)을 골랐다. 비용이 거의 0 이 되는 건 부수 효과고, 진짜 이유는 배포가 코드의 숨은 가정을 드러내주기 때문이다.

**가정 ①: "인스턴스는 하나다".** 수집 중복 가드의 상태가 `_last_cycle_at` 이라는 모듈 전역 변수였다. 인스턴스 A 가 "방금 수집했다"고 기억해도 B 는 모른다. 이게 왜 심각한가는 7월 20일에 계산해둔 호출량 예산과 붙여 보면 나온다 — 인프로세스 루프에서는 **시계의 개수 = 프로세스의 개수**이므로 예산에 인스턴스 수라는 곱셈 항이 붙고, 재난문자(1,000건/일)는 14.4% → 43%(3인스턴스)로 뛴다. **확장이 곧 한도 초과가 되는 구조.** 재미있는 건 LLM 쿨다운에 대해서는 "상태가 프로세스 메모리라 다중 인스턴스면 Redis 로 옮겨야 한다"고 이미 적어뒀는데, **같은 한계가 ingest 가드에도 있다는 걸 인식하지 못했다**는 점이다. 한 곳에서 배운 교훈이 같은 모양의 다른 코드에 자동으로 적용되지는 않는다.
→ `ingest_runs` 테이블을 만들어 가드 상태를 옮겼다. 부수 효과로 실행 이력이 남는다(언제 몇 건, 어떤 소스 실패, `finished_at` NULL = 도중에 죽은 사이클). 남은 한계도 적어둔다: 두 인스턴스가 같은 순간 조회하면 둘 다 통과하는 read-then-write 경합은 막지 않는다 — 외부 cron 이 단일 호출자라 위험이 낮고, 필요해지면 DB 락으로 좁힌다.

**가정 ②: "호출하는 사람은 나뿐이다".** `POST /events/ingest` 가 무인증이었다. 7월 20일 일지에도 이 엔드포인트를 "무방비"라고 적어놨는데, 다시 보니 **그때의 위협 모델은 "내가 실수로 연타하는 것"이었고 그래서 해법이 시간 가드였다.** 공개 배포에서의 위협은 "주소를 아는 타인이 고의로 반복 호출해 우리 공공 API 쿼터와 LLM 비용을 태우는 것"이고, 여기엔 시간 가드가 답이 아니다 — **가드는 낭비를 줄이지만 인증이 아니다.** 같은 코드, 같은 "무방비"라는 단어인데 조건(로컬 → 공개)이 바뀌면서 필요한 대응이 달라졌다.
→ `X-Ingest-Token` 헤더 인증. 선택 근거 둘: (a) Cloud Run 의 IAM 인증이 더 정석처럼 보이지만 **서비스 단위 all-or-nothing** 이라 공개 페이지(`/login`·`/app`)를 같이 서빙하는 서비스에는 쓸 수 없다(웹/잡을 별도 서비스로 쪼개면 가능하지만 인프라 증가로 보류). (b) 토큰 미설정 시 **열어두지 않고 503**(fail-closed) — "설정을 잊으면 열려 있는" 보호는 없는 것보다 위험하다. 로컬 자동 수집은 스케줄러가 서비스 함수를 직접 호출하므로 영향 없고, 막히는 건 HTTP 수동 트리거뿐이다.

**테스트가 잡아낸 버그 하나.** 잘못된 토큰을 한글로 보내는 테스트를 썼더니 401 이 아니라 500 이 났다. `secrets.compare_digest` 는 **비ASCII 문자열에 TypeError** 를 던진다. HTTP 헤더는 latin-1 로 디코드되므로 그런 값이 실제로 도착할 수 있어서 진짜 결함이다(다만 httpx 는 한글 헤더를 애초에 못 보내므로, 테스트는 raw bytes 를 보내 실제 와이어 상황을 재현하도록 고쳤다). bytes 로 인코딩해 비교하도록 수정 + 회귀 테스트.

**컨테이너에서 잡은 함정: `--proxy-headers` 만으로는 부족하다.** 어제 터널에서 배운 교훈("`--proxy-headers` 없으면 OAuth 리다이렉트가 http 로 생성됨")을 Dockerfile 에 그대로 옮겼는데, 이미지를 만들어 실제로 호출해 보니 `X-Forwarded-Proto: https` 를 보내도 여전히 `redirect_uri=http://...` 가 나왔다. 원인은 uvicorn 이 **신뢰 목록(기본 `127.0.0.1`)에서 온 X-Forwarded-* 만 반영**한다는 것 — 어제 터널이 통했던 건 cloudflared 가 localhost 에서 붙어서였고, **Cloud Run 은 프록시 IP 가 달라 그대로 배포하면 로그인이 다시 깨질 자리였다.** `--forwarded-allow-ips=*`(플랫폼 LB 만 컨테이너에 닿을 수 있는 환경에서의 "앞단을 신뢰한다" 선언) 추가 후 재검증: http → `http://`, `X-Forwarded-Proto: https` → `https://`. **어제 실기기에서 통했다는 게 오늘 다른 환경에서 통한다는 뜻이 아니다.**

**마이그레이션을 컨테이너 기동에 넣지 않기로 했다.** 흔한 패턴은 entrypoint 에서 `alembic upgrade head` 를 돌리는 것인데, 서버리스에서는 컨테이너가 자주 새로 뜨므로 **매 콜드 스타트마다 DB 왕복이 추가**되고, 인스턴스 여럿이 동시에 DDL 을 걸 수 있다. 배포 시 1회 별도 실행으로 정했다 — 콜드 스타트를 아끼는 결정이 곧 배포 절차를 한 단계 늘리는 결정이라는 트레이드오프.

**FCM 자격증명을 환경변수로도 받게 했다.** 로컬은 `secrets/*.json` 파일이 편하지만 PaaS 엔 파일을 올릴 곳이 없다. `FCM_CREDENTIALS_JSON`(내용 자체)을 추가하고 파일보다 우선하게 했다 — "배포 환경에 남은 낡은 파일 경로에 끌려가지 않도록". 마스킹 대상(`_collect_secrets`)에도 추가했다. private_key 가 들어있으니까.

**콜드 스타트: "무엇이 느려지는가"를 나눠서 판단했다.** 처음 설명할 때 "유휴 15분이면 꺼지고, 그래도 10분 cron 이 두드리니 대체로 따뜻하다"고 말했는데, 이 두 문장은 나란히 두면 앞뒤가 안 맞는다(형인이 바로 지적했고, 정확히는 이렇다).
- 구글은 **유휴 컨테이너 회수 타이밍을 공개하지 않는다** — "15분"은 관측치일 뿐 보장이 아니다.
- 회수 시점이 cron 주기(10분)보다 **길면** cron 이 도착할 때 컨테이너가 살아 있고 타이머가 리셋된다. 그래서 **콜드 스타트 비용은 사용자가 아니라 cron 이 낸다**(배치가 3초 늦는 건 문제가 아니다). 반대로 회수가 더 빠르면 둘 다 콜드를 맞는다. 즉 "대체로"는 **확률이고, 그 확률을 정하는 값을 구글이 공개하지 않으므로 숫자로 말할 수 없다.** 대신 사용자가 확실히 콜드를 맞는 경우는 열거할 수 있다 — 배포 직후, 크래시 직후, cron 이 실패한 뒤, 회수 직후, 요청이 몰려 인스턴스가 추가로 뜰 때.
- **가장 중요한 구분: 푸시 알림은 콜드 스타트와 무관하다.** 알림은 FCM(구글 서버)이 폰으로 보내고, 우리 서버는 발송을 요청하는 순간에만 필요한데 그 순간은 cron 이 방금 깨운 시점이라 이미 따뜻하다. **특보가 왔는데 알림이 늦는 일은 없다.** 느려지는 건 사람이 페이지를 여는 순간뿐이고, 이 서비스는 구독 설정할 때 한 번 오고 몇 주 안 온다.
→ 그래서 대응을 **로딩 표시**로 정했다(`min-instances=1` 은 유일한 보장이지만 유휴 과금이 붙어 "거의 무료"를 포기하는 결정). 여기에도 한계가 있다: **로딩 표시가 덮는 건 "페이지가 뜬 뒤 API 를 기다리는 구간"뿐이다.** 콜드 스타트로 HTML 자체를 기다리는 구간은 우리 JS 가 실행되기 전이라 손댈 수 없고, 그 구간은 브라우저 탭의 로딩 표시가 담당한다. DB 도 잠든다는 점이 겹칠 수 있다(Neon 무료 티어는 유휴 시 대기 → 깨우는 지연 추가). 최종 판단은 배포 후 `curl -w "%{time_total}"` 로 콜드/웜을 **재서** 하기로 했다 — 추정으로 결정하지 않는다.

**기록의 빈틈이 드러난 순간.** 배포 준비를 마치고 "GCP 계정·프로젝트를 생성하세요"라고 안내했는데, 형인이 "1번은 저번에 이미 해놨던 것 같은데 기록에 없었어?"라고 물었다. 맞는 지적이었다 — **Firebase 프로젝트는 GCP 프로젝트다.** 이름과 콘솔 UI 만 다르고 같은 자원이라, 07-22 에 FCM 서비스계정을 발급받은 시점에 `hazard-fighter` GCP 프로젝트가 이미 생성돼 있었다(구글 OAuth 클라이언트를 만든 곳도 같은 프로젝트 안이다). 그런데 노트에는 "Firebase 콘솔에서 서비스계정 발급", "구글 콘솔에서 OAuth 클라이언트 생성"이라는 **행위**만 적혀 있고 그 결과로 **어떤 자원이 생겼는지**가 없었다. 그래서 이미 있는 것을 새로 만들라고 안내하는 일이 벌어졌다.
→ 교훈: **외부 콘솔 작업은 "무엇을 눌렀나"가 아니라 "무엇이 생겼고 서로 어떤 소유 관계인가"로 기록해야 한다.** 안 적어두면 같은 자원을 중복 생성하거나(빈 프로젝트가 늘어남) 엉뚱한 곳에서 설정을 찾느라 헤맨다.

**그리고 그 자원 관계를 적자마자 내가 또 틀렸다.** "FCM 과 구글 OAuth 클라이언트가 둘 다 `hazard-fighter` 프로젝트에 있다"고 썼는데, 확인해 보니 아니었다. 검증 방법이 재미있다 — **OAuth client_id 의 앞 숫자가 프로젝트 번호**이고, **FCM 웹 설정의 messagingSenderId 도 프로젝트 번호**다. `gcloud projects list` 의 번호와 맞춰보니:

| 자원 | 프로젝트 번호 | 프로젝트 |
|---|---|---|
| FCM(서버·웹 양쪽) | 608692423557 | `hazard-fighter` |
| 구글 OAuth 클라이언트 | 480606898875 | `hazard-fighter-503307` (표시 이름 "hazard fighter") |

즉 **두 자원이 서로 다른 프로젝트에 흩어져 있었다.** 콘솔에서 이름이 비슷한 프로젝트(`hazard fighter` / `hazard-fighter` / AI Studio 가 자동 생성한 `gen-lang-client-…`)가 여러 개 만들어져 있었기 때문이다. 기능상 문제는 없다 — OAuth 클라이언트는 client_id/secret 로 동작하므로 Cloud Run 이 다른 프로젝트에 있어도 로그인은 정상이다. 다만 **배포 후 리다이렉트 URI 를 추가하러 갈 곳은 `hazard-fighter-503307` 프로젝트의 "사용자 인증 정보" 화면**이고, 이걸 모르면 `hazard-fighter` 프로젝트에서 OAuth 클라이언트를 찾다가 "없어졌나?" 하고 헤매게 된다. 정확히 이런 걸 적어두라는 얘기였다.
→ 교훈 하나 더: **"아마 같은 프로젝트일 것"이라고 적지 말고 확인해서 적는다.** 다행히 확인 수단이 자원 ID 안에 들어 있었다(client_id·appId 접두 번호).

**Cloud Run 은 FCM 이 있는 `hazard-fighter` 에 배포한다** — 푸시가 서비스의 본체이고, 나중에 서비스계정 JSON 대신 Workload Identity 로 넘어갈 여지도 같은 프로젝트일 때 생긴다. 그리고 Firebase 무료(Spark) 플랜에는 결제 계정이 없고 **Cloud Run 은 결제 계정 연결이 필수**라, "프로젝트 생성"이 아니라 "기존 프로젝트에 결제 연결"이 실제 남은 일이었다(이미 갖고 있던 Firebase 결제 계정을 연결해 해결 — 새 카드 등록 불필요).

**배포 첫 명령에서 6개월 묵은 시한폭탄이 터졌다.** Neon 에 `alembic upgrade head` 를 돌리자 `column "auth_provider" already exists` 로 죽었다. 0001 이 `Base.metadata.create_all()` 이라 **"그 시점 스키마"가 아니라 "지금 모델 전체"** 를 만들고, 뒤이어 0002 가 중복 컬럼을 추가하려다 실패한 것. 로컬 DB 는 리비전을 순서대로 밟아와서 멀쩡했기 때문에 **"업그레이드 경로"만 테스트되고 "빈 DB 신규 생성 경로"는 한 번도 테스트되지 않았다** — 그리고 배포는 정확히 후자다. 0001 을 명시적 DDL 로 다시 쓰고, 결과를 모델과 대조하는 `scripts/verify_schema.py` 로 검증했다(첫 실행에서 내 실수 7건 — `created_at` nullable 누락 — 을 잡아냈다). 자세한 내용은 3-5 참고.

**결과.** 테스트 138개 통과, 컨테이너에서 `/login` 200 / 토큰 없는 ingest 401 / 올바른 토큰 200 / 프록시 https 리다이렉트까지 검증. Neon 에 마이그레이션 체인 재생 후 스키마 13개 테이블이 모델과 일치 확인. DB 는 Neon(무료 티어, 싱가포르) — 앱은 pooled 접속, 마이그레이션은 direct 접속.

**면접 한마디.** "배포는 코드가 조용히 깔고 있던 가정을 드러내는 단계였습니다. '인스턴스는 하나'라는 가정 위에 있던 중복 가드를 DB 로 옮기고, '호출자는 나뿐'이라는 가정 위에 있던 무인증 엔드포인트에 토큰 인증을 붙였습니다. 특히 같은 엔드포인트를 두고 실수 연타와 타인의 고의는 다른 위협이며 시간 가드는 후자의 답이 아니라는 점, 어제 터널에서 통한 프록시 설정이 다른 환경에서는 통하지 않는다는 점을 컨테이너에서 직접 확인해 잡았습니다."

### 2026-07-27 — 실배포: 맥이 꺼져도 도는 서비스가 됐다 (Cloud Run + Cloud Scheduler)

**배포 자체는 명령 하나였다.** `gcloud run deploy --source .` 가 Cloud Build 로 Dockerfile 을 빌드해 Artifact Registry 에 넣고 Cloud Run 에 올린다. 미리 해둔 준비(§배포 준비 항목) 덕에 코드 수정 없이 한 번에 떴다. 옵션은 전부 앞선 결정의 반영 — `asia-southeast1`(Neon 싱가포르와 동일 지역: 앱↔DB 거리 > 사용자↔앱 거리), `--min-instances 0`(거의 무료 유지), `--max-instances 2`(폭주가 과금이 되지 않게 하는 안전핀), `--cpu-boost`(콜드 스타트 단축), `SCHEDULER_ENABLED=0`(시계는 이제 Cloud Scheduler 가 담당). 시크릿은 `.env`→YAML 변환 스크립트로 `--env-vars-file` 에 실어 화면에 찍히지 않게 했고, 소스 업로드도 `.gcloudignore` 로 `.env`·`secrets/` 를 명시적으로 차단했다 — .gitignore 자동 변환 같은 "알아서 잘 되겠지"에 시크릿을 맡기지 않는다.

**설계가 실전에서 그대로 재현됐다.** 검증 순서대로: ① `--forwarded-allow-ips` 수정 덕에 OAuth 리다이렉트가 https 로 생성 ② 토큰 없는 ingest 401, 실토큰 200 — 첫 사이클에 실데이터 **133건**이 Neon 에 저장 ③ 직후 재호출은 "최근 49초 전에 수집됨" 스킵 — **DB 가드가 (다른 인스턴스일 수도 있는) 프로세스 간에 동작** ④ Cloud Scheduler 10분 주기 등록 후 13:50 정규 실행이 자율로 돌아 신규 0건·중복 133건 스킵 — 이벤트 dedupe 도 프로덕션 확인. 도메인은 Search Console 소유 확인(TXT) → Cloud Run 도메인 매핑 → Cloudflare CNAME 을 터널→`ghs.googlehosted.com`(DNS only) 전환, 인증서 자동 발급까지 약 11분. **`hazard.peterju.cloud` 를 그대로 쓴 덕에 OAuth 콘솔은 손도 안 댔다** — 콜백 URI 가 도메인 기준이라 터널 시절 등록값이 그대로 유효. 주소를 고정 도메인으로 잡아둔 7월 23일의 결정이 여기서 이자를 쳤다.

**해외 IP 차단 — 배포 지역이 데이터 소스를 죽일 수 있다.** 첫 사이클부터 홍수통제소(hrfco)만 `ConnectTimeout`. 같은 키로 로컬(한국 IP)에선 1.8초에 200 이 오고, 10분 간격 2회 연속 싱가포르에서만 타임아웃 — **hrfco.go.kr 이 해외 IP 를 차단**하는 것으로 판단했다(data.go.kr 계열은 해외에서도 정상). 대응 옵션 셋을 놓고 **수용**을 골랐다: ① 현재 hrfco 소스는 청주 관측소 2곳 하드코딩이고 실구독 지역은 대전이라 실질 손실 0건 ② 홍수 상황은 기상특보(호우)·긴급재난문자가 겹으로 커버 ③ 소스별 에러 격리 덕에 나머지 파이프라인 무손상. 서울 리전 이전(한국 IP 확보)은 Neon 이 서울에 없어 **모든 DB 쿼리에 +70ms** 를 내는 트레이드오프라, "홍수 관측소 동적 선정" 작업 때 실측으로 재검토한다. 교훈: **공공 API 연동 서비스는 배포 지역 선택이 기능 가용성 문제가 된다** — 리전을 고를 때 "DB 와의 거리"만 봤지 "데이터 소스가 나를 받아주는가"는 체크리스트에 없었다.

**콜드 스타트 실측 — 재보니 걱정보다 훨씬 좋았다.** 약속대로 추정 대신 측정: 웜 응답 **0.3초 안팎**(한국↔싱가포르 RTT 포함). 그리고 예상 못 한 발견 — **새 리비전을 배포하면 startup probe 가 인스턴스를 미리 띄워두므로, 배포 직후 첫 요청도 0.32초**였다. 즉 사용자가 부팅을 기다리는 경우는 "scale-to-zero 후 첫 방문"뿐인데, cron 이 10분마다 두드려서 그 상태를 실측으로 만들어내기도 어려웠다(관찰된 최악값: 최초 배포 직후 0.62초). 결론: 로딩 표시로 충분하고 `min-instances=1` 은 불필요 — "재서 결정한다"고 했고, 재봤더니 결정할 것도 없었다.

**데이터는 옮기지 않는다.** 로컬 Postgres 의 계정·구독·기기 토큰(형인 폰)은 Neon 으로 이관하지 않았다. 사용자 1명·구독 1건이라 pg_dump 이관은 과하고, **폰에서 새로 로그인→구독하는 것 자체가 프로덕션 end-to-end 재검증**이 된다. 폰에 남은 옛 JWT 는 Neon 에 그 사용자가 없으므로 401→자동 로그아웃→로그인 화면으로 흘러간다 — 미리 만들어둔 401 처리 경로가 마이그레이션 UX 까지 커버한 셈.

**폰으로 프로덕션 end-to-end 재검증 (같은 날 밤, 5단계 전부 통과).** ① 폰에서 `/app` 을 열자 옛 JWT 가 401 을 받고 자동 로그아웃 → 로그인 화면. **DB 를 옮기지 않기로 한 결정이 여기서 검증됐다** — 계정이 사라진 상황이 곧 "토큰은 유효한데 사용자가 없는" 경로이고, 미리 만들어둔 401 처리가 그걸 조용히 흡수했다. ② 소셜 로그인(지난번 프로바이더 배지 표시) ③ 보호 대상·지역 등록 + 알림 권한 ④ **구독 직후 backfill 알림 생성 → 푸시 수신** — 수집·판단·문구 생성·FCM 발송이 전부 클라우드에서 돌아 폰까지 닿았다 ⑤ **카톡으로 링크를 보내 인앱 브라우저에서 열자 노란 배너와 "Chrome·Safari 로 열기" 버튼이 실제로 떴다** — 오전에 UA 위조로만 확인했던 인앱 감지가 진짜 카카오톡 웹뷰에서 검증됐다(오전 노트에 "상시 가동 후 확인"이라고 남겨둔 항목을 같은 날 닫았다).

**오늘 하루의 구조.** 아침엔 인앱 브라우저 배너(첫 사용자의 첫 화면), 낮엔 배포 준비(코드가 깔고 있던 가정 두 개), 저녁엔 실배포와 재검증. 세 작업이 별개처럼 보이지만 **전부 "로컬에서만 참인 가정을 찾아 없애는 일"** 이었다 — 브라우저는 하나가 아니고(인앱), 인스턴스도 하나가 아니고(가드), 호출자도 나 혼자가 아니고(인증), 마이그레이션의 시작점도 항상 기존 DB 가 아니다(빈 DB). 배포란 그 가정들을 한꺼번에 청구서로 받는 순간이었다.

**면접 한마디.** "배포는 준비된 코드를 올리는 마지막 명령이 아니라 검증의 연속이었습니다. 프록시 신뢰, 엔드포인트 인증, DB 가드, dedupe 가 프로덕션에서 재현되는 걸 단계별로 확인했고, 예상 밖의 발견 — 데이터 소스의 해외 IP 차단 — 은 손실 범위를 정량화한 뒤 수용을 선택했습니다. 콜드 스타트는 추정 대신 실측으로 결론냈는데, cron 워밍과 배포 시 사전 기동 덕에 사용자 체감 문제가 사실상 없다는 결과였습니다."

### 2026-07-30 — 3일 뒤에 프로덕션을 열어봤다: 죽지 않은 채 멈춰 있던 알림

**점검을 먼저 하기로 했다.** 다음 작업(쿠폰/결제)으로 넘어가기 전에, 배포하고 3일이 지났으니 로그·요청·알림·비용을 한 번 다 보자고 했다. 딱히 이상 신호가 있어서가 아니라 "상시 가동으로 바뀌었으니 상시로 보는 습관을 만들자"는 쪽이었는데, 결과적으로 이게 이번 주 가장 중요한 작업이 됐다.

**겉보기 지표는 전부 초록불이었다.** Cloud Scheduler 401회 전부 200, 3일간 785 요청에 **5xx 0건**, 웜 응답 0.25~0.36초, 로그의 API 키는 전부 `***REDACTED***`(마스킹 정상), 이벤트 2,265건 수집·dedupe 78,716건 차단. 여기까지만 보면 "잘 돌고 있네"로 끝날 상황이었다.

**그런데 DB 를 세어보니 등록된 기기 토큰이 0개였다.** 미발송 알림 8건, 마지막 발송은 이틀 전(7월 29일 오전 10시). 그 8건에는 대전 폭염특보(HIGH) 3건, 화재위험경보·열대야 재난문자가 들어 있었다 — **수집·판단·LLM 문구 생성까지 다 해놓고 폰으로는 한 건도 안 간 상태**로 이틀을 보냈다.

**원인은 두 겹이었고, 둘 다 구조적인 것이었다.**

첫 번째. 토큰을 지우는 코드 경로는 하나뿐이다 — FCM 이 404 UNREGISTERED 를 주면 dispatch 가 죽은 토큰으로 보고 삭제한다. **이 로직 자체는 옳다.** 문제는 **다시 만드는 경로가 "구독 폼 제출" 하나뿐**이었다는 것. 웹푸시 토큰은 원래 죽는다(사이트 데이터 삭제, 브라우저의 구독 갱신, 장기 미사용). 즉 **"언젠가 반드시 일어나는 일"에 대해 정리는 자동, 복구는 수동**이었고, 그러면 시간은 한 방향으로만 흐른다 — 토큰은 사라지기만 하고 돌아오지 않는다. 더 나쁜 게 있었다. 클라이언트가 발급받은 토큰을 localStorage 에 캐시하고 **캐시가 있으면 FCM 에 다시 묻지 않았다.** 그래서 사용자가 "구독 추가"를 다시 눌러도 죽은 값이 재등록되고 다음 발송에서 또 지워진다 — **스스로 못 낫는 상태**였다.

두 번째. 이걸 이틀간 아무도 몰랐던 이유는 **로그가 한 줄도 없었기 때문이다.** `ingest.py` 와 dispatch 에 logger 가 아예 없었다. 왜 없어도 됐었나를 따져보면 이유가 분명하다 — 로컬에서는 스케줄러가 서비스 함수를 **직접 호출**하고 결과 dict 를 콘솔에서 눈으로 봤다. 그런데 Cloud Scheduler 로 옮기면서 그 dict 는 **HTTP 응답으로 나가고 Scheduler 는 그걸 버린다.** 3-25 에 "시계를 밖으로 뺐다"고 썼는데, 그때 같이 빠져나간 게 하나 더 있었던 것이다 — **결과를 보던 사람.** 배포 준비 때 "인스턴스는 하나다", "호출자는 나뿐이다" 두 가정을 찾아 없앴는데, **"결과는 누군가 보고 있다"는 세 번째 가정**은 놓쳤다.

**고친 것도 그 둘이다(P1+P2 를 한 배포로).** 로그를 먼저 넣었다 — 고쳤는지 확인할 수단이 먼저 있어야 하니까. 사이클 끝에 한 줄 요약(INFO), 그리고 **사람이 알아야 하는 상황만 WARNING**: 죽은 토큰 정리 / 보낼 기기 없음 / 발송 실패. 여기서 규칙을 하나 세웠다 — **정상일 때는 조용해야 한다.** 모든 사이클이 경고를 뿜으면 아무도 안 읽으니, "전부 발송 성공이면 WARNING 이 0건"인 것까지 테스트로 고정했다(`test_dispatch_stays_quiet_when_all_sent`). 복구 쪽은 `/app` 을 열 때마다 현재 토큰을 FCM 에 물어 서버와 맞추게 했다. 서버 등록이 멱등이라(`crud.register_device_token`) 무조건 POST 해도 안전하고, 캐시는 "이 기기에서 알림을 켠 적 있나" 힌트로만 남겼다. 화면에는 "✅ 이 기기로 알림을 받는 중이에요" 배지를 붙였다 — 조용한 실패를 사용자도 볼 수 있게. 여기서 지킨 제약: **페이지 로드 시 권한을 요청하지는 않는다.** 권한 팝업은 클릭 직후 첫 await 여야 하고(7월 22일 함정), 자동 팝업은 사용자를 놀라게 한다. 그래서 "이미 granted 인 경우에만 토큰을 맞춘다".

**배포 직후 로그가 이렇게 나왔다** — 설계한 대로 세 줄이 한꺼번에 보인다.

```
WARNING app.services.ingest:  수집 실패 [hrfco_flood]: ConnectTimeout: timed out
WARNING app.services.dispatch: 보낼 기기가 없어 대기 중인 알림 8건 (등록된 기기 토큰 없음)
INFO    app.services.ingest:  수집 사이클 완료: 신규 6 · 중복 251 · 알림생성 0 · 발송 0/8
                              (대기 8, 실패 0, 토큰정리 0) · 실패한 소스: ['hrfco_flood']
```

이전에는 이 상황이 로그상 **완전히 무음**이었다. 이제는 한 줄만 봐도 "왜 안 갔는지"가 보인다.

**밀린 8건은 발송하지 않기로 했다.** 토큰이 복구되는 순간 8건이 한꺼번에 쏟아지는데, 그중 2건은 3년 전(2023년 9월) 호우 문자였다(아래 P3). 폰이 알림 폭탄을 맞는 것도, 3년 전 경보가 지금 울리는 것도 알림 신뢰도를 깎는다. **삭제하지 않고 `sent_at` 만 찍어** 발송 가드를 통과시켰다 — 되돌리려면 다시 NULL 로 바꾸면 되고, 사고의 증거는 남는다.

**비용도 실측했다.** 결론은 전부 무료 한도 안이지만, 눈에 걸리는 항목이 하나 있었다.

| 항목 | 실측 | 무료 한도 대비 |
|---|---|---|
| Cloud Run CPU | 3,816 vCPU-초/일 (144사이클 × 26.5초) | **64%** — hrfco 를 끄면 28% |
| Cloud Run 메모리 / 요청 | 57,000 GiB-초/월 / 약 5,000 요청/월 | 16% / 0.25% |
| 공공 API | 720회/일 시도 | 키별 한도 내 |
| LLM | 3일간 18회 (문구 생성만, Layer 2 는 0회) | ≈ $0 |
| Neon | 11 MB | 저장은 여유 (컴퓨트 시간은 콘솔 확인 필요) |

**hrfco 타임아웃 15초가 평균 사이클 26.5초의 57%** 였다. 어차피 클라우드에서 못 쓰는 소스 하나가 컴퓨팅의 절반 이상을 먹고 있다는 뜻이다. 3일 전에는 "실질 손실 0건"으로 수용했는데, **수용의 대가가 데이터 손실이 아니라 컴퓨팅 예산이라는 게 이제 숫자로 보인다** — 판단을 뒤집을 정도는 아니지만, 다음 정리 대상 목록의 맨 위로 올라갔다.

**같이 발견한 것들(다음 작업으로).** ① **신선도 필터가 없다** — 공공 API 가 `crtDt=20260728` 요청에 2023년 9월 레코드 185건을 돌려준 사이클이 있었고, 그게 알림 2건까지 만들었다. cutoff 는 `backfill_subscription`(48시간)에만 있고 평상시 경로엔 없다. 상류가 이상한 값을 주는 건 못 막지만 **그게 사용자 폰까지 가는 건 막을 수 있다.** ② **재난문자 페이지 경계 유실** — "총건수로 마지막 페이지만 읽기" 구조에서 total 이 100 경계를 넘으면 직전 페이지 뒷부분(최대 99건)을 아무도 안 읽는다. 마지막 페이지 + 직전 페이지를 같이 읽으면 되고 dedupe 가 있으니 중복은 무해하다. ③ `/` 가 404(3일간 89건), WordPress 스캔 봇이 훑고 감.

**면접 한마디.** "배포 3일 뒤 점검에서, 헬스체크·에러율·응답속도가 전부 정상인데 알림만 이틀째 안 나가고 있는 걸 발견했습니다. 원인은 두 겹이었습니다. 죽은 푸시 토큰을 정리하는 코드는 있었지만 재생성 경로가 특정 사용자 행동에만 걸려 있어 한 번 끊기면 영구히 복구되지 않는 구조였고, 그걸 이틀간 몰랐던 이유는 주기 실행을 외부 스케줄러로 옮기면서 결과를 사람이 보는 경로가 함께 사라졌기 때문이었습니다. 결과 요약 로그와 '정상일 때는 조용하다'는 경고 기준을 넣고, 정리 코드마다 '무엇이 이걸 다시 만들어주나'를 짝지어 자동 복구 경로를 만들었습니다. 같은 점검에서 비용도 실측해, 실패하는 데이터 소스 하나의 타임아웃이 컴퓨팅의 57%를 쓰고 있다는 것까지 숫자로 확인했습니다."

## Part 6. 용어 사전

- **백엔드** — 사용자 눈에 안 보이는 서버 쪽 프로그램. 데이터 저장·처리·응답 담당.
- **API** — 프로그램끼리 데이터를 주고받는 약속. REST는 그중 URL+HTTP동사 방식.
- **엔드포인트** — API의 각 주소별 처리 지점 (예: `POST /persons`).
- **ORM** — 파이썬 객체 ↔ DB 표를 자동 변환해주는 도구 (SQLAlchemy).
- **모델** — DB 표 구조 정의 (`app/models/`).
- **스키마** — API 입출력 형태 정의 (`app/schemas/`, Pydantic).
- **PK(기본키)** — 행을 유일하게 구분하는 값.
- **FK(외래키)** — 다른 표의 행을 가리키는 값. 표 간 관계.
- **마이그레이션** — DB 구조 변경 이력을 파일로 관리 (Alembic).
- **세션** — DB와의 대화 창구.
- **트랜잭션** — "전부 성공 아니면 전부 취소" 단위.
- **commit / flush / rollback** — 확정 / 임시반영(id 확보용) / 취소.
- **다이얼렉트(dialect)** — SQLAlchemy가 각 DB의 방언 차이를 다루는 개념.
- **UUID** — 전 세계에서 안 겹치는 긴 고유 id.
- **JSONB** — Postgres의 JSON 저장/검색 전용 타입.
- **mock** — 실제 대신 쓰는 가짜 데이터/동작.
- **추상 클래스(ABC)** — 상속받는 클래스가 특정 메서드를 반드시 구현하게 강제하는 틀.
- **컨테이너 / Docker** — 앱+실행환경을 상자에 담아 어디서나 동일 실행.
- **시크릿** — API 키·비밀번호 등 유출되면 안 되는 값.
- **asyncio / 이벤트 루프** — 파이썬 비동기 실행 프레임워크. 여러 작업을 번갈아 실행.
- **lifespan** — FastAPI의 서버 시작/종료 훅. 백그라운드 작업을 켜고 끄는 자리.
- **폴링(polling)** — 주기적으로 "새 데이터 있나?" 물어보는 방식.
- **quota(호출 한도)** — API 제공자가 정한 최대 호출 수. 초과 시 거부·차단.
- **폴백(fallback)** — 1순위가 실패했을 때 대신 쓰는 예비 수단.
- **서킷 브레이커 / 쿨다운** — 실패한 대상에 반복 호출하지 않게 일정 시간 격리하는 패턴.
- **멱등(idempotent)** — 같은 요청을 여러 번 보내도 결과가 같음 (예: 중복 구독 생성 → 기존 반환).
- **캐시(cache)** — 한 번 계산/조회한 결과를 기억해 재사용. 비용·시간 절약.
- **감사 로그(audit log)** — "왜 그런 결정이 났는지" 추적할 수 있게 남기는 기록 (ai_risk_logs).
- **가드(guard)** — 조건이 안 맞으면 실행을 막는 방어 코드 (예: 최근 수집했으면 스킵).

## Part 7. 블로그 소재 아이디어

이 프로젝트에서 뽑을 만한 글감:

1. **"운영은 Postgres, 테스트는 SQLite" — with_variant로 두 마리 토끼 잡기** (3-7). 실전 문제→해결이 뚜렷해서 가장 반응 좋을 소재.
2. **키 발급을 기다리지 않고 개발하기 — mock fallback 패턴** (3-9). 외부 API 의존 프로젝트의 공통 고민.
3. **위험도를 규칙과 LLM 2계층으로 나눈 이유** (3-10). 비용·지연·예측가능성 트레이드오프 이야기.
4. **실수로 커밋한 API 키, 히스토리에서 지우기 — git filter-repo 실전** (3-13). 짧고 실용적.
5. **모델 vs 스키마, 왜 두 벌로 나눌까** (3-4). 입문자가 자주 헷갈리는 주제라 검색 수요 있음.
6. **유료 LLM이 죽으면? 폴백 체인 + 쿨다운 실전기** (3-16). insufficient_quota를 실제로 겪고 해결한 스토리라 생생함.
7. **API 한도로부터 설계하기 — 호출량 예산과 폴링 주기** (3-15). "감이 아니라 계산"이라는 메시지가 명확함.
8. **규칙 + LLM 하이브리드로 위험도 판단하기** (3-16). matrix/ai 알림이 나란히 찍힌 실증 스크린샷이 킬러 콘텐츠.
9. **로그에 API 키가 새고 있었다 — 로깅 필터로 시크릿 마스킹** (3-17). 짧고 실용적, 발견 스토리가 있음.
